# ATRAG

RAG для португальских налоговых документов с вопросами и ответами на русском, английском и португальском.

Первая версия ограничена содержимым одного загруженного CIRS.pdf: извлечение, структура, фрагменты и поиск с цитатами и страницами. Исторические редакции и проверка периодов вынесены в будущие задачи.

Стек: Python, LangGraph, Streamlit, OpenAI API, PostgreSQL и расширение pgvector. Настройки подключения и API-ключи загружаются из корневого `.env`.

Решение от 30.10.2026: PostgreSQL выбран основным хранилищем источника, структуры документа, фрагментов, метаданных и embeddings. Векторный поиск выполняется через pgvector, полнотекстовый - средствами PostgreSQL; результаты объединяются в гибридном поиске. Исходный PDF хранится в файлах или объектном хранилище, с проверяемыми ссылками из базы.

Согласованный доступ к БД: SQLAlchemy 2.x, Psycopg 3, пакет `pgvector`, Alembic и `langgraph-checkpoint-postgres`; настройки читает `python-dotenv`. Первая версия использует синхронные подключения, пул соединений и отдельную сессию для каждой операции. Подробности - в [плане взаимодействия с БД](docs/document-ingestion/README.md#библиотеки-и-взаимодействие-с-бд).

Реализованы Шаги 1–8 плана `document-ingestion`: подготовка PDF, embeddings с постоянным кешем, переносимый пакет, атомарная индексация, гибридный поиск и воспроизводимая оценка. Приёмка выявила пропуски основных условий статьи 16 и ограничения контекста; критерии качества MVP пока не выполнены. По согласованию живая проверка OpenAI ограничена тремя фрагментами и тремя запросами. Полный корпус проверен с подставными векторами; качество настоящих embeddings по всему CIRS не измерено. Подробнее — в [отчёте приёмки](docs/document-ingestion/ACCEPTANCE.md). Вторая часть проекта — чат с поисковым инструментом. Поиск возвращает содержание явно указанного снимка документа и не требует налогового года.

Схемы данных находятся в `src/atrag/schemas`: настройки — в `settings.py`, артефакты подготовки — в `ingestion/`, контракт поиска — в `retrieval.py`. Сервисы подготовки, переноса и индексации находятся в `src/atrag/ingestion/services/`; чистые преобразования — в `src/atrag/ingestion/`, поиск — в `src/atrag/retrieval/`, ORM-модели — в `db_models.py`, миграции — в `src/atrag/migrations/`.

Решение от 30.10.2026: PDF подготавливается локально — снимок, извлечение, OCR, ручная сверка, разбор структуры, фрагменты и embeddings. На прод передаётся проверенный пакет PDF, подготовленных данных и метаданных; там выполняются индексация в PostgreSQL и проверка поиска. Документы доставляются отдельно от Git. Tesseract и `por.traineddata` нужны в среде подготовки. Для импорта пакета на сервере достаточно самого пакета, приложения, `DATABASE_URL` и `ATRAG_DATA_DIR`; локальный реестр не требуется. Управление выпусками корпуса и обязательный граф с checkpoints отложены.

Для запуска нужен Python 3.14 и `uv`:

```sh
uv sync --locked
cp .env.example .env
uv run atrag config check
```

В `.env` укажите `DATABASE_URL` для своей базы на уже запущенном локальном PostgreSQL. Формат — `postgresql://user:password@localhost:5432/database`; для локальной аутентификации через сокет подходит `postgresql:///database`. Пароль из шаблона — заглушка. Ключ OpenAI понадобится на этапе embeddings.

`atrag config check` проверяет настройки и `data/sources/cirs.json`, выводит безопасный JSON без API-ключа и DSN. Команда работает без базы и ключа OpenAI; признаки `database_configured` и `openai_configured` показывают наличие настроек. Переменные процесса имеют приоритет над `.env`, относительный `ATRAG_DATA_DIR` отсчитывается от корня проекта. Загрузчик `atrag.settings.load_settings()` общий для CLI и будущего Streamlit-приложения.

Реестр содержит португальский оригинал, URL со статусом `candidate` и известную отметку редакции сборника. Неизвестные даты получения и изменения нормы остаются `null`. Реестр хранится в Git; `.env`, промежуточные данные и отчёты исключены.

Импорт локального PDF в неизменяемый снимок:

```sh
uv run atrag ingest snapshot
# Другой зарегистрированный источник:
uv run atrag ingest snapshot --registry data/sources/another.json
```

Путь `local_path` из реестра отсчитывается от корня проекта; абсолютный путь тоже допустим. Команда сохраняет точные байты в `ATRAG_DATA_DIR/raw/<sha256>/source.pdf` и `manifest.json` рядом. Манифест содержит `SourceSnapshot`: идентификатор и SHA-256, размер, путь относительно каталога данных, фактический `ingested_at` в UTC и исходный реестр в поле `source`. Неизвестный `downloaded_at` остаётся `null`; URL не становится подтверждённым. Проверяются сигнатура `%PDF-` и ожидаемая контрольная сумма из реестра; разбор содержимого PDF относится к следующему шагу.

Каждая попытка получает отдельный UUID `run_id` и `runs/<run_id>/manifest.json` со статусом `running`, `succeeded` или `failed`, временем начала/завершения и происхождением этой попытки. Повторный импорт проверяет сохранённые байты и манифест, возвращает `reused: true` и сохраняет дату первого импорта. Изменённые байты образуют новый снимок, если соответствуют контрольной сумме реестра. Одновременные импорты публикуют один полный снимок; незавершённый или повреждённый сохранённый снимок вызывает ошибку без перезаписи. После прерывания процесса журнал может остаться в `running`; повторный запуск получает новый `run_id`.

Импорт работает без подключения к БД и вызовов OpenAI. Скачивание по URL пока не реализовано; требования проверки домена, HTTP-статуса, MIME, сигнатуры, размера и таймаута остаются обязательными для будущего загрузчика.

Извлечение страниц, координат и таблиц из снимка:

```sh
uv run atrag ingest inspect --no-ocr
# Португальский OCR и проверенные таблицы этого снимка CIRS:
uv run atrag ingest inspect --source docs/CIRS.pdf \
  --tessdata-dir data/ocr/tessdata \
  --review data/sources/cirs-extraction-review.json
```

`inspect` сначала создаёт или проверяет снимок, затем записывает отдельный запуск в `ATRAG_DATA_DIR/runs/<run_id>/`. В нём находятся `pages.jsonl`, объединённые `tables.json`, `report.json`, `manifest.json`, вырезанные изображения и исходные результаты OCR в `images/`. Каждая строка `pages.jsonl` содержит физический номер страницы от 1, печатные обозначения, размеры страницы, исходный текст, строковые блоки с координатами и шрифтами, нормализованный текст, части таблиц, изображения и замечания. Координаты `bbox = [x0, top, x1, bottom]` измеряются в пунктах PDF от левого верхнего угла. Повторяющиеся колонтитулы и печатные номера остаются в блоках происхождения, но удаляются из нормализованного текста. Жёсткие дефисы сохраняются; автоматически склеиваются только мягкие переносы.

Для OCR нужны локальный `tesseract` и португальская модель `por.traineddata`. Можно установить языковые данные системы или скачать [модель из официального tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast/blob/main/por.traineddata) в отдельный каталог:

```sh
mkdir -p data/ocr/tessdata
curl --fail --location --max-time 60 \
  https://raw.githubusercontent.com/tesseract-ocr/tessdata_fast/main/por.traineddata \
  -o data/ocr/tessdata/por.traineddata
```

OCR запускается локально с `-l por`, без БД, OpenAI и сетевых вызовов. Манифест сохраняет версии библиотек, Tesseract, разрешение рендера и SHA-256 явно указанной языковой модели. Если Tesseract или язык отсутствуют, OCR не завершается либо отключён через `--no-ocr`, изображение остаётся в отчёте для проверки. Непроверенный OCR не попадает в нормализованный текст.

В CIRS таблица 68 объединяется через физические страницы 81–82 с сохранением двух уровней заголовков, единиц и девяти строк. Файл `cirs-extraction-review.json` содержит ручной эталон этой таблицы и транскрипцию изображения 68-A: OCR ошибочно распознаёт `2,5` как `25`. Эталон привязан к SHA-256 PDF и координатам; несовпадение снимка или извлечённой текстовой таблицы останавливает запуск. Проверенная таблица изображения вставляется в своё место перед следующим пунктом, а исходный OCR сохраняется отдельно. Эта сверка подтверждает соответствие таблицы содержимому PDF.

Реальный прогон обработал 139 страниц; после сверки таблиц 68/68-A статус документа остаётся `needs_review`: обложка не имеет текстового слоя, а ещё одна таблица на странице 117 состоит из двух изображений с ненадёжным OCR. Эти области перечислены в `report.json`. Повторный запуск создаёт отдельный каталог; потребитель должен проверять `status: succeeded` в его манифесте. При ошибке фиксируется `failed`, при прерывании процесса возможен `running`.

Разбор структуры готового извлечения без повторного PDF/OCR:

```sh
uv run atrag ingest parse --extracted data/runs/<extraction_run_id>/manifest.json
# Для другого реестра того же семейства CIRS:
uv run atrag ingest parse --extracted data/runs/<extraction_run_id>/manifest.json \
  --registry data/sources/another.json
```

`parse` проверяет успешное завершение извлечения, целостность исходного снимка,
контрольную сумму реестра, последовательность физических страниц и согласованность
частей таблиц. Новый каталог `data/runs/<run_id>/` содержит `legal_units.jsonl`,
`tables.json`, `report.json` и `manifest.json`. Манифест сохраняет версию парсера,
SHA-256 входных и выходных артефактов и время в UTC. Исходное извлечение не меняется;
повторный разбор создаёт новый запуск с теми же содержательными артефактами.

`LegalUnit` — адрес положения независимо от редакции; в промежуточном JSON он также
содержит текст этого вхождения и локаторы снимка. Примеры разных адресов:
`pt:decreto-lei:442-a/88:approving_decree:article:16` и
`pt:cirs:code:article:16:paragraph:1:subparagraph:a`. Идентификаторы не зависят от
SHA-256, текста и даты запуска. Родительские единицы содержат текст дочерних норм;
`parent_id` сохраняет иерархию. Примечания и цитаты переходных положений представлены
отдельными единицами с явной ролью и не добавляются в текст родительской нормы.
Отсылки и примечания об изменении закреплены за непосредственно содержащим их
положением; локаторы сохраняют физические страницы, печатные обозначения и координаты.

Парсер учитывает расположение и шрифты заголовков, исключает оглавление, различает
декрет, преамбулу и CIRS, главы/разделы, `2`/`2-A`, пункты, подпункты и вложенные
списки. Таблицы сохраняют ячейки и связи с пунктами. Точные и относительные отсылки
разрешаются только в доступной структуре; внешние и неоднозначные остаются
`unresolved` с исходным текстом. Указанные в PDF отменённые положения получают
`legal_status: repealed`; остальные сохраняют `unknown`. Проверочный образец описан
в [tests/fixtures/cirs](tests/fixtures/cirs/README.md).

Полный CIRS даёт 213 статей: 17 в декрете и 196 в кодексе. Успешный разбор сохраняет
`review_status: needs_review` и `validity_status: unknown`: это структурный результат.
Неизвестная применимость не блокирует подготовку фрагментов. Подтверждение
исторических периодов вынесено за пределы первой версии.

Формирование фрагментов из успешного разбора:

```sh
uv run atrag ingest chunk --parsed data/runs/<parse_run_id>/manifest.json
```

`chunk` проверяет контрольные суммы трёх артефактов разбора и исходного PDF,
сохраняет `fragments.jsonl`, `report.json` и манифест в новом каталоге запуска.
Основной фрагмент — номерной пункт с подпунктами или ненумерованная статья.
Длинный текст делится на части с точными диапазонами исходных символов.
В `embedding_text` повторяются название документа, область акта, адрес,
родительское вводное условие и короткое оформление. Примечания индексируются
отдельно; адресаты отсылок загружаются явно. Перекрытия
соседних статей нет. `text_original` сохраняет исходную формулировку выбранной
единицы, `context` — тексты и локаторы добавленного контекста.

Полный текст вместе с контекстом измеряется через [tiktoken](https://github.com/openai/tiktoken),
кодировка `cl100k_base`; её словарь нужно предварительно закешировать для работы
без сети. Параметры `ATRAG_CHUNK_TARGET_TOKENS` и `ATRAG_CHUNK_MAX_TOKENS` задают
цель 700 и максимум 1200. Неделимый блок сверх максимума или блок с непроверенной
таблицей исключается из поискового текста с явной записью в `omissions`;
`uncovered_unit_ids` перечисляет непокрытые единицы исходного разбора.
Статус `needs_review` и неизвестная применимость не исключают остальные фрагменты.
Идентификаторы зависят от снимка, текста, контекста, версии и параметров разбиения;
время и идентификатор запуска в них не входят. Повторные запуски дают одинаковые
содержательные артефакты. БД, OCR и OpenAI API на этом этапе не вызываются.

Подготовка embeddings:

```sh
# DATABASE_URL указывает БД с установленным серверным pgvector.
uv run atrag db migrate
# Для отсутствующих в кеше текстов нужен OPENAI_API_KEY; команда вызывает платный API.
uv run atrag ingest embed --chunked data/runs/<chunk_run_id>/manifest.json
```

По умолчанию используются `text-embedding-3-small`, 1536 измерений и пакеты по 32
текста. Перед запросом сервис проверяет SHA-256 артефактов, снимок и происхождение
фрагментов, пересчитывает хеш точного `embedding_text` и токены `cl100k_base`.
Пределы API: 8192 токена на текст, 2048 текстов и 300 000 токенов на запрос;
ограничения взяты из [официальной документации OpenAI](https://developers.openai.com/api/reference/resources/embeddings/methods/create).
Пустой ввод, неверная модель, размерность или индексы ответа останавливают этап.

Таблица `embeddings` хранит векторы pgvector с уникальным ключом
`(model, dimensions, input_hash)`. Одинаковые тексты оплачиваются один раз;
повторный запуск полностью из кеша работает без API-ключа. Каждый успешный пакет
фиксируется отдельно, поэтому после ошибки повтор использует уже сохранённые
векторы. Писатели одного пространства модели и размерности выполняются по очереди
через PostgreSQL advisory lock; во время HTTP-запроса транзакция БД не открыта.
Смена модели или размерности создаёт отдельное пространство.

Временные сетевые ошибки, HTTP 408/409/429 и 5xx получают до трёх попыток с
задержкой и jitter. Ошибки авторизации, данных и `insufficient_quota` завершают
запуск. Новый `runs/<run_id>/` содержит `embeddings.jsonl`, `report.json` и
`manifest.json` с контрольными суммами, версиями, временем UTC и статусом.
Каждая строка embeddings связывает снимок и фрагмент с ключом кеша и вектором;
float32-представление совпадает до и после чтения pgvector. Отчёт сохраняет
известный расход токенов, число запросов/повторов, попадания в кеш и исходные
замечания chunk. При обрыве до фиксации пакета API может потребоваться повторно;
расход запроса без полученного ответа неизвестен.

Кеш допускает 3072 измерения `text-embedding-3-large`, но поисковые индексы разных
пространств нужно создавать отдельно: стандартные HNSW/IVFFlat для `vector`
ограничены 2000 измерениями; для больших векторов требуется другая конфигурация
по [документации pgvector](https://github.com/pgvector/pgvector#what-if-i-want-to-index-vectors-with-more-than-2000-dimensions).
Поисковая схема первой версии принимает только 1536 измерений. Для large нужно явно выбрать 1536 при подготовке embeddings. Пакет с другой размерностью отклоняется до записи; автоматического смешивания или преобразования векторов нет.

Перенос и индексация подготовленного документа:

```sh
# Локально, после завершения parse, chunk и embed:
uv run atrag ingest package \
  --parsed data/runs/<parse_run_id>/manifest.json \
  --chunked data/runs/<chunk_run_id>/manifest.json \
  --embedded data/runs/<embed_run_id>/manifest.json \
  --review data/sources/cirs-extraction-review.json \
  --output data/packages/cirs

# Скопируйте весь data/packages/cirs в каталог доставки на сервере.
# На сервере, с его DATABASE_URL и ATRAG_DATA_DIR:
uv run atrag db migrate
uv run atrag ingest index --package /srv/delivery/cirs/manifest.json
```

Пакет содержит `source.pdf`, `snapshot.json`, `legal_units.jsonl`, `tables.json`,
`fragments.jsonl`, `embeddings.jsonl`, манифесты и отчёты трёх этапов, а также
переданные `--review` ручные сверки. `--review` можно повторять или опустить,
если сверок нет. `manifest.json` перечисляет относительные пути, SHA-256,
версии обработки и пространство embeddings. Исторические пути в метаданных
источника сохраняются как сведения о подготовке и не используются при импорте.

Создание и импорт проверяют контрольные суммы, успешность и связь этапов,
происхождение, структуру родителей, ссылки, таблицы и соответствие векторов
фрагментам. Повторное создание идентичного пакета возвращает прежний каталог;
другое содержимое требует нового назначения. Индексация сохраняет проверенный
PDF в `ATRAG_DATA_DIR/raw`, затем одной транзакцией заменяет полный набор
данных этого снимка, включая связи и записи кеша. Повтор не создаёт дубликаты,
ошибка оставляет предыдущий индекс доступным. Писатели одного снимка
выполняются последовательно; читатели получают согласованное состояние.
Вызовов модели и повторного PDF/OCR-разбора при импорте нет.

Поиск по явно указанному снимку:

```sh
# Точные адреса работают без OPENAI_API_KEY.
uv run atrag search 'CIRS 16' --snapshot <snapshot_id> --language ru
uv run atrag search 'art. 53 CIVA' --snapshot <snapshot_id> --language pt

# Смысловой запрос вызывает API для одного query embedding.
uv run atrag search 'How is tax residency determined?' \
  --snapshot <snapshot_id> --language en --limit 5 --context-tokens 6000
```

Точные варианты `artigo 53.º CIVA`, `art. 53 CIVA`, `CIVA 53` нормализуются
в адрес; для отсутствующего кодекса возвращается `no_match` с причиной
`document_not_loaded:CIVA`. Доступны фильтры CLI `--code`, `--article`, `--scope`.
Смысловой поиск использует модель и размерность индекса, точный cosine search
и взвешенный португальский FTS (`unit_title` A, `document_title` B, текст D),
затем RRF с `ATRAG_RRF_K` (по умолчанию 60). Обе ветви используют одинаковые
фильтры снимка и адреса и окно по 50 кандидатов на ветвь. `--mode vector`,
`--mode fts` и `--mode hybrid` позволяют сравнить ветви; по умолчанию используется
hybrid. FTS обходится без OpenAI. Настройки окна и RRF сохранены до полной
оценки настоящих embeddings. HNSW пока не создаётся.

Сервис `search_tax_documents(query, limit=5, query_language=None, *, snapshot_id,
engine, client=None, filters=None, context_tokens=6000, rrf_k=60, mode="hybrid")` возвращает
португальские части, цитаты, страницы, источник, таблицы выбранной части,
родительские вводные условия и доступные адреса ссылок. Бюджет считает текстовые
свидетельства и таблицы; координаты PDF и служебные метаданные в него не входят.
Отсылки перечислены в `available_reference_ids` и `fragment.references`; их
наличие не загружает тексты адресатов. Для продолжения, оригинала, примечания,
выбранных отсылок и проверенных цепочек исключений доступны отдельные функции
с явным бюджетом. Контракты и примеры: [части](docs/document-ingestion/PARTS.md)
и [расширение контекста](docs/document-ingestion/CONTEXT.md).

`--language` принимает `ru`, `en`, `pt`; для короткого адреса требуется язык
интерфейса. Для полного вопроса без языка используются эвристики: кириллица —
`ru`, португальские признаки — `pt`, иначе `en`. Их качество ещё требует оценки.
Язык вопроса не фильтрует язык документа. Отчёт результата сохраняет известные
пропуски, непокрытые единицы, проблемы таблиц и неразрешённые ссылки.

Историческая приёмка Шага 8 сохранена отдельно. Исправления разбиения и
контекста проходят новую локальную приёмку с синтетическими векторами;
смысловое качество настоящей модели ещё не измерено. Подробности и оставшиеся
ограничения — в [отчёте](docs/document-ingestion/ACCEPTANCE.md).

Оценка подготовленного и уже проиндексированного пакета:

```sh
uv run atrag evaluate --package data/packages/cirs/manifest.json \
  --benchmark docs/document-ingestion/benchmark-v2.json --context-tokens 6000
```

Эталон версии 2 содержит 36 поисковых случаев на `ru`, `en`, `pt`: 18 смысловых
и 18 точных; ещё 18 случаев отдельно проверяют оригинал, примечания, исключения
и выбранную статью с обеими таблицами. Адреса, страницы, выдержки, роли и строки таблиц сверяются с
пакетом до поиска. Для проверки конкретного пункта эталон передаёт обычные
структурированные фильтры сервиса.

`evaluate` выполняет поисковые случаи в трёх режимах с limit=5, а случаи
расширения — без вызовов модели, с бюджетом из каждого явного запроса. Для полного
эталона это 36 вызовов query embeddings; эта команда не создаёт embeddings
корпуса. Такой живой прогон в Шаге 8 не выполнялся. В
`ATRAG_DATA_DIR/runs/<run_id>/` сохраняются исходные ответы, `report.json` и
манифест с SHA-256 входов/выходов. Сводка разделяет языки и режимы: попадание
ожидаемого положения в top-5, доля успешных точных случаев, полнота обязательного
контекста, совпадение цитат, median/p95 задержки и токены API. Провал случая
записывается в `passed` и `failed_case_ids`; успешное завершение команды
означает завершённое измерение. При ошибке остаются завершённые случаи и
`failed`-манифест. Происхождение векторов нельзя вывести из результата поиска:
поле `vector_provenance` явно оставлено непроверенным. `expansion_records`
содержит отдельные результаты полноты и цитат для выбранных операций.

Модульные проверки:

```sh
uv run pytest -m 'not integration'
uv run ruff check src tests
uv run ruff format --check src tests
```

Интеграционные проверки используют отдельную локальную базу `atrag_test_context_20261101` повторно. Тестовые таблицы очищаются между прогонами; саму базу после задачи не удалять. Для первого запуска при отсутствии базы создать её и включить `vector`; расширение устанавливается отдельно от Python-пакета `pgvector` по [официальной инструкции](https://github.com/pgvector/pgvector#installation).

```sh
# Только если база ещё не существует:
createdb atrag_test_context_20261101
psql -d atrag_test_context_20261101 -c 'CREATE EXTENSION IF NOT EXISTS vector'
# Последующие прогоны используют эту же базу:
ATRAG_TEST_DATABASE_URL=postgresql://localhost/atrag_test_context_20261101 uv run pytest
```

Без `ATRAG_TEST_DATABASE_URL` интеграционные тесты пропускаются. Они проверяют миграции, ограничения, кеш, атомарную индексацию, смену модели, повторное разбиение, конкурирующих писателей, изоляцию снимков, FTS и RRF-поиск. Также сохранены проверки восстановления соединения и Psycopg-пула checkpointer. HTTP-запросы httpx в тестах заблокированы; API проверяется через `MockTransport`, без живой модели и оплаты. Проверено на Python 3.14.6, PostgreSQL 16.13 и pgvector 0.8.7; версии Python-зависимостей закреплены в `uv.lock`.
