# ATRAG

RAG для португальских налоговых документов с вопросами и ответами на русском, английском и португальском.

Первая версия ограничена содержимым одного загруженного CIRS.pdf: извлечение, структура, фрагменты и поиск с цитатами и страницами. Исторические редакции и проверка периодов вынесены в будущие задачи.

Стек: Python, LangGraph, Streamlit, OpenAI API, PostgreSQL и расширение pgvector. Настройки подключения и API-ключи загружаются из корневого `.env`.

Решение от 30.10.2026: PostgreSQL выбран основным хранилищем источника, структуры документа, фрагментов, метаданных и embeddings. Векторный поиск выполняется через pgvector, полнотекстовый - средствами PostgreSQL; результаты объединяются в гибридном поиске. Исходный PDF хранится в файлах или объектном хранилище, с проверяемыми ссылками из базы.

Согласованный доступ к БД: SQLAlchemy 2.x, Psycopg 3, пакет `pgvector`, Alembic и `langgraph-checkpoint-postgres`; настройки читает `python-dotenv`. Первая версия использует синхронные подключения, пул соединений и отдельную сессию для каждой операции. Подробности - в [плане взаимодействия с БД](docs/document-ingestion/README.md#библиотеки-и-взаимодействие-с-бд).

Реализованы Шаги 1–4 плана `document-ingestion`: типизированные настройки, реестр CIRS, настройка синхронного подключения SQLAlchemy, неизменяемый снимок PDF, извлечение с сохранением расположения и разбор юридической структуры. Следующий шаг — Шаг 5, формирование поисковых фрагментов; затем embeddings, индексация и проверка поиска. Первая часть проекта — подготовка PDF и поиска; вторая — чат с поисковым инструментом. В первой версии поиск не требует налогового года и возвращает содержание явно указанного снимка документа.

Схемы данных находятся в `src/atrag/schemas`: настройки — в `settings.py`, модели источников, снимков, извлечения, OCR и юридической структуры — в `ingestion/`. Загрузка настроек остаётся в `src/atrag/settings.py`. Сервисы загрузки реестров, импорта снимков, извлечения PDF, OCR и запуска структурного разбора находятся в `src/atrag/ingestion/services/`; чистые преобразования и парсеры — в `src/atrag/ingestion/`.

Решение от 30.10.2026: PDF подготавливается локально — снимок, извлечение, OCR, ручная сверка, разбор структуры и формирование фрагментов. На прод передаётся проверенный пакет PDF, подготовленных данных и метаданных; там выполняются индексация в PostgreSQL и проверка поиска. Код и реестры доставляются вместе с приложением, документы и артефакты — отдельно от Git в `ATRAG_DATA_DIR`. Tesseract и `por.traineddata` нужны в локальной среде подготовки; поисковому приложению на проде они не требуются. Упаковка, доставка и индексация пока не реализованы. Управление выпусками корпуса и обязательный граф с checkpoints отложены.

Для запуска нужен Python 3.14 и `uv`:

```sh
uv sync --locked
cp .env.example .env
uv run atrag config check
```

В `.env` укажите `DATABASE_URL` для своей базы на уже запущенном локальном PostgreSQL. Формат — `postgresql://user:password@localhost:5432/database`; для локальной аутентификации через сокет подходит `postgresql:///database`. Пароль из шаблона — заглушка. Ключ OpenAI понадобится на этапе embeddings.

`atrag config check` проверяет настройки и `data/sources/cirs.json`, выводит безопасный JSON без API-ключа и DSN. Команда работает без базы и ключа OpenAI; признаки `database_configured` и `openai_configured` показывают наличие настроек. Переменные процесса имеют приоритет над `.env`, относительный `ATRAG_DATA_DIR` отсчитывается от корня проекта. Загрузчик `atrag.settings.load_settings()` общий для CLI и будущего Streamlit-приложения.

Реестр содержит португальский оригинал, URL со статусом `candidate` и известную отметку редакции сборника. Неизвестные даты получения и изменения нормы остаются `null`. Реестр хранится в Git; `.env`, промежуточные данные и отчёты исключены.

Импорт локального PDF в неизменяемый снимок:

```sh
uv run atrag ingest snapshot
# Другой зарегистрированный источник:
uv run atrag ingest snapshot --registry data/sources/another.json
```

Путь `local_path` из реестра отсчитывается от корня проекта; абсолютный путь тоже допустим. Команда сохраняет точные байты в `ATRAG_DATA_DIR/raw/<sha256>/source.pdf` и `manifest.json` рядом. Манифест содержит `SourceSnapshot`: идентификатор и SHA-256, размер, путь относительно каталога данных, фактический `ingested_at` в UTC и исходный реестр в поле `source`. Неизвестный `downloaded_at` остаётся `null`; URL не становится подтверждённым. Проверяются сигнатура `%PDF-` и ожидаемая контрольная сумма из реестра; разбор содержимого PDF относится к следующему шагу.

Каждая попытка получает отдельный UUID `run_id` и `runs/<run_id>/manifest.json` со статусом `running`, `succeeded` или `failed`, временем начала/завершения и происхождением этой попытки. Повторный импорт проверяет сохранённые байты и манифест, возвращает `reused: true` и сохраняет дату первого импорта. Изменённые байты образуют новый снимок, если соответствуют контрольной сумме реестра. Одновременные импорты публикуют один полный снимок; незавершённый или повреждённый сохранённый снимок вызывает ошибку без перезаписи. После прерывания процесса журнал может остаться в `running`; повторный запуск получает новый `run_id`.

Импорт работает без подключения к БД и вызовов OpenAI. Скачивание по URL пока не реализовано; требования проверки домена, HTTP-статуса, MIME, сигнатуры, размера и таймаута остаются обязательными для будущего загрузчика.

Извлечение страниц, координат и таблиц из снимка:

```sh
uv run atrag ingest inspect --no-ocr
# Португальский OCR и проверенные таблицы этого снимка CIRS:
uv run atrag ingest inspect --source docs/CIRS.pdf \
  --tessdata-dir data/ocr/tessdata \
  --review data/sources/cirs-extraction-review.json
```

`inspect` сначала создаёт или проверяет снимок, затем записывает отдельный запуск в `ATRAG_DATA_DIR/runs/<run_id>/`. В нём находятся `pages.jsonl`, объединённые `tables.json`, `report.json`, `manifest.json`, вырезанные изображения и исходные результаты OCR в `images/`. Каждая строка `pages.jsonl` содержит физический номер страницы от 1, печатные обозначения, размеры страницы, исходный текст, строковые блоки с координатами и шрифтами, нормализованный текст, части таблиц, изображения и замечания. Координаты `bbox = [x0, top, x1, bottom]` измеряются в пунктах PDF от левого верхнего угла. Повторяющиеся колонтитулы и печатные номера остаются в блоках происхождения, но удаляются из нормализованного текста. Жёсткие дефисы сохраняются; автоматически склеиваются только мягкие переносы.

Для OCR нужны локальный `tesseract` и португальская модель `por.traineddata`. Можно установить языковые данные системы или скачать [модель из официального tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast/blob/main/por.traineddata) в отдельный каталог:

```sh
mkdir -p data/ocr/tessdata
curl --fail --location --max-time 60 \
  https://raw.githubusercontent.com/tesseract-ocr/tessdata_fast/main/por.traineddata \
  -o data/ocr/tessdata/por.traineddata
```

OCR запускается локально с `-l por`, без БД, OpenAI и сетевых вызовов. Манифест сохраняет версии библиотек, Tesseract, разрешение рендера и SHA-256 явно указанной языковой модели. Если Tesseract или язык отсутствуют, OCR не завершается либо отключён через `--no-ocr`, изображение остаётся в отчёте для проверки. Непроверенный OCR не попадает в нормализованный текст.

В CIRS таблица 68 объединяется через физические страницы 81–82 с сохранением двух уровней заголовков, единиц и девяти строк. Файл `cirs-extraction-review.json` содержит ручной эталон этой таблицы и транскрипцию изображения 68-A: OCR ошибочно распознаёт `2,5` как `25`. Эталон привязан к SHA-256 PDF и координатам; несовпадение снимка или извлечённой текстовой таблицы останавливает запуск. Проверенная таблица изображения вставляется в своё место перед следующим пунктом, а исходный OCR сохраняется отдельно. Эта сверка подтверждает соответствие таблицы содержимому PDF.

Реальный прогон обработал 139 страниц; после сверки таблиц 68/68-A статус документа остаётся `needs_review`: обложка не имеет текстового слоя, а ещё одна таблица на странице 117 состоит из двух изображений с ненадёжным OCR. Эти области перечислены в `report.json`. Повторный запуск создаёт отдельный каталог; потребитель должен проверять `status: succeeded` в его манифесте. При ошибке фиксируется `failed`, при прерывании процесса возможен `running`.

Разбор структуры готового извлечения без повторного PDF/OCR:

```sh
uv run atrag ingest parse --extracted data/runs/<extraction_run_id>/manifest.json
# Для другого реестра того же семейства CIRS:
uv run atrag ingest parse --extracted data/runs/<extraction_run_id>/manifest.json \
  --registry data/sources/another.json
```

`parse` проверяет успешное завершение извлечения, целостность исходного снимка,
контрольную сумму реестра, последовательность физических страниц и согласованность
частей таблиц. Новый каталог `data/runs/<run_id>/` содержит `legal_units.jsonl`,
`tables.json`, `report.json` и `manifest.json`. Манифест сохраняет версию парсера,
SHA-256 входных и выходных артефактов и время в UTC. Исходное извлечение не меняется;
повторный разбор создаёт новый запуск с теми же содержательными артефактами.

`LegalUnit` — адрес положения независимо от редакции; в промежуточном JSON он также
содержит текст этого вхождения и локаторы снимка. Примеры разных адресов:
`pt:decreto-lei:442-a/88:approving_decree:article:16` и
`pt:cirs:code:article:16:paragraph:1:subparagraph:a`. Идентификаторы не зависят от
SHA-256, текста и даты запуска. Родительские единицы содержат текст дочерних норм;
`parent_id` сохраняет иерархию. Примечания и цитаты переходных положений представлены
отдельными единицами с явной ролью и не добавляются в текст родительской нормы.
Отсылки и примечания об изменении закреплены за непосредственно содержащим их
положением; локаторы сохраняют физические страницы, печатные обозначения и координаты.

Парсер учитывает расположение и шрифты заголовков, исключает оглавление, различает
декрет, преамбулу и CIRS, главы/разделы, `2`/`2-A`, пункты, подпункты и вложенные
списки. Таблицы сохраняют ячейки и связи с пунктами. Точные и относительные отсылки
разрешаются только в доступной структуре; внешние и неоднозначные остаются
`unresolved` с исходным текстом. Указанные в PDF отменённые положения получают
`legal_status: repealed`; остальные сохраняют `unknown`. Проверочный образец описан
в [tests/fixtures/cirs](tests/fixtures/cirs/README.md).

Полный CIRS даёт 213 статей: 17 в декрете и 196 в кодексе. Успешный разбор сохраняет
`review_status: needs_review` и `validity_status: unknown`: это структурный результат.
Неизвестная применимость не блокирует поиск по документу. Формирование поисковых
фрагментов, embeddings, запись в БД и поиск ещё не реализованы; подтверждение
исторических периодов вынесено за пределы первой версии.

Модульные проверки:

```sh
uv run pytest -m 'not integration'
uv run ruff check src tests
uv run ruff format --check src tests
```

Интеграционные проверки используют отдельную временную базу с именем `atrag_test_*` на локальном сервере. В ней должен быть включён `vector`; расширение устанавливается отдельно от Python-пакета `pgvector` по [официальной инструкции](https://github.com/pgvector/pgvector#installation).

```sh
createdb atrag_test_ingestion
psql -d atrag_test_ingestion -c 'CREATE EXTENSION vector'
ATRAG_TEST_DATABASE_URL=postgresql:///atrag_test_ingestion uv run pytest
dropdb atrag_test_ingestion
```

Без `ATRAG_TEST_DATABASE_URL` интеграционные тесты пропускаются. Они проверяют векторный поиск и откат через SQLAlchemy/Psycopg, восстановление соединения и отдельный Psycopg-пул checkpointer. Проверено на Python 3.14.6, PostgreSQL 16.13 и pgvector 0.8.7; версии Python-зависимостей закреплены в `uv.lock`.
