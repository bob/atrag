# План реализации админки

Дата подготовки: 2026-11-11.

Админка встраивается в существующий Streamlit-интерфейс. Основа уже есть:
Google-вход, таблица пользователей, сохранённый usage чата и метаданные
документов. Основная работа — права доступа, деактивация, дата последнего
входа и две административные страницы.

## Проверенная техническая основа

Проверка выполнена по текущему коду и существующим тестовым сценариям.
Содержимое production-базы и полнота исторического usage отдельно не проверялись.

| Показатель | Что уже реализовано | Что добавить для админки |
|---|---|---|
| LLM-токены пользователя | `chat_turns.model_usage` хранит `requests`, `input_tokens`, `output_tokens`, `total_tokens`; ход связан с пользователем через `chat_conversations.user_id` | SQL-агрегацию по пользователям и отображение; отдельная таблица счётчиков не требуется |
| Размер исходника | `source_snapshots.size_bytes` хранит размер PDF либо сумму размеров HTML-страниц | Выборку и суммирование уникальных исходников без повторного учёта между версиями |

Сбор LLM usage выполняется в
[`chat/api/agent.py`](../../src/atrag/chat/api/agent.py), запись завершённого
хода — в [`chat/db/execution.py`](../../src/atrag/chat/db/execution.py),
сохранение доступного usage при обработанной ошибке — в
[`chat/services/turns.py`](../../src/atrag/chat/services/turns.py).
Существующие сценарии сохранения и возобновления проверяются в
[`test_chat_turns.py`](../../tests/integration/test_chat_turns.py).

Если провайдер не вернул usage, текущий сборщик подставляет нули для
отсутствующих счётчиков. Жёсткое завершение процесса также может помешать
записи в строку хода. Поэтому эти данные подходят для показа учтённого расхода,
но сами по себе не гарантируют полного совпадения со счётом провайдера.

Размер исходников записывается при индексировании в
[`ingestion/services/index.py`](../../src/atrag/ingestion/services/index.py).
Для HTML сумма размеров страниц определяется в
[`schemas/ingestion/collections.py`](../../src/atrag/schemas/ingestion/collections.py).
По уточнению пользователя на странице Documents требуется только размер
исходника. Для этого достаточно сохранённого `size_bytes`.

## 1. Правила доступа и данные

Добавить в `.env`:

```dotenv
ATRAG_ADMIN_EMAILS=admin@example.com,second@example.com
```

Разбирать список через существующий `Settings`: проверять адреса, убирать
пробелы, приводить к нижнему регистру и удалять дубли. Пустой список означает
отсутствие администраторов.

Роль вычислять по подтверждённому Google email. Отдельное поле `role` в БД
не нужно: единственным источником назначения администраторов остаётся env.

Предлагаемые правила:

- Текущая проверка `allowed_emails` сохраняется: при включённом списке допуска
  администратор тоже должен в него входить.
- Деактивация запрещает доступ независимо от роли.
- Изменение списка администраторов применяется после перезапуска приложения.
- Пользователь по-прежнему определяется через `(issuer, subject)`, поэтому
  совпадение email не объединяет аккаунты.

**Проверка:** тесты разбора настройки, назначения роли и взаимодействия
с текущим допуском.

## 2. Статус пользователя и учёт входов

Миграцией расширить `chat_users`:

| Поле | Назначение |
|---|---|
| `is_active` | Активен ли аккаунт; существующим пользователям выставить `true` |
| `last_login_at` | Последний успешный вход; для старых записей первоначально `NULL` |

Дата регистрации уже есть в `created_at`.

Последним входом считать начало новой авторизованной сессии приложения,
включая вход по сохранённой Google cookie. Сейчас авторизация вызывается
при каждом обновлении Streamlit, поэтому обновление `last_login_at` нужно
отделить от регулярной проверки доступа: клики и отправка сообщений не должны
менять дату входа.

Повторная авторизация не должна активировать заблокированный аккаунт.
До первого входа после миграции показывать «Нет данных».

**Проверка:** миграция сохраняет пользователей и историю; новая сессия
обновляет дату, обычный rerun — нет.

## 3. Административные операции и блокировка

Выделить небольшой модуль `atrag/admin`: схемы результатов, сервис и запросы
к БД. В интерфейсе оставить отображение и обработку действий.

На каждом административном вызове проверять действующие права пользователя
на сервере. Скрытого переключателя в интерфейсе недостаточно.

Для изменения статуса использовать операцию вида
`set_user_active(user_id, active)`: повторное выполнение устанавливает тот же
статус. Предлагается запретить администратору деактивировать самого себя.

Блокировка должна действовать и для открытых сессий: после неё нельзя читать
историю, создавать диалоги, отправлять или возобновлять запросы. Уже
отправленный провайдеру LLM-запрос может завершиться; его статус и расход
токенов необходимо сохранить.

**Проверка:** обычный и деактивированный пользователь не могут вызвать
административные операции напрямую; старая сессия теряет доступ после
блокировки.

## 4. Навигация

Разделить нынешний sidebar на общую часть и меню выбранного режима.

Для администратора:

```text
Чат | Админка

В режиме «Админка»:
• Users
• Documents
```

Справа отображать выбранную страницу. Начальной страницей админки сделать
`Users`.

Использовать нативную навигацию Streamlit. При переходах сохранять выбранный
диалог; возвращение в чат должно открывать его снова. Открытие
административной страницы напрямую также должно проходить проверку прав.

**Проверка:** переключение режимов и страниц, сохранение диалога, отказ
в доступе по прямому адресу.

## 5. Страница Users

Таблица:

| Email | Зарегистрирован | Последний вход | Статус | LLM input | LLM output | LLM total |
|---|---|---|---|---:|---:|---:|

Для выбранного пользователя добавить действие «Деактивировать» или
«Активировать». После успешной записи обновлять таблицу.

Токены суммировать по сохранённому `chat_turns.model_usage` через принадлежащие
пользователю диалоги:

- Учитывать все LLM-вызовы внутри хода, включая вызовы инструментов.
- Учитывать сохранённый расход неуспешных и прерванных ходов.
- Исключить двойной подсчёт при повторном открытии или возобновлении.
- Embeddings показывать отдельно, если они понадобятся: сейчас это другой
  показатель.

В интерфейсе назвать показатель «Учтённые LLM-токены»: исторические вызовы
без полученного usage невозможно достоверно восстановить. Отдельный
накопительный счётчик создавать не нужно.

Добавить поиск по email, фильтр статуса и постраничную загрузку. Агрегацию
выполнять в БД одним запросом на страницу.

**Проверка:** несколько пользователей и диалогов, отсутствие запросов,
failed/interrupted-ходы, повторное выполнение и реактивация без потери истории.

## 6. Страница Documents

Показывать все загруженные документы, включая неопубликованные. Одна строка —
логический документ `source_id`; версии доступны в деталях.

| Документ | Загружен | Формат | Исходники | Размер исходника | Опубликован |
|---|---|---|---|---:|---|

Определения:

- **Загружен:** `indexed_at`, когда версия установлена в эту БД. Существующий
  `ingested_at` может относиться к более ранней подготовке исходника.
- **Исходники:** ссылка на источник и скачивание сохранённого PDF либо ZIP
  с HTML-файлами.
- **Размер исходника:** сохранённый `source_snapshots.size_bytes` — размер
  PDF либо сумма размеров HTML-страниц. При объединении версий в строку
  документа суммировать уникальные исходники по `source_sha256`; общий
  исходник нескольких версий считать один раз. Отображать размер в удобных
  единицах.

В деталях показывать версии и их даты. Файлы читать только при скачивании
из проверенного каталога хранения. Отсутствующий исходник отмечать отдельно,
сохраняя доступность таблицы.

**Проверка:** размер PDF, сумма размеров страниц HTML-коллекции, несколько
версий с общими исходниками без двойного подсчёта, неопубликованный документ
и отсутствующий файл.

## 7. Приёмка и подготовка выпуска

Каждый этап выполнять по `ub-mode`: сначала падающий поведенческий тест,
затем минимальная реализация и проверка.

Итоговые проверки:

- Интеграционные тесты на `atrag_test_context_20261101`, с очисткой тестовых
  таблиц. Базу не пересоздавать и не удалять; создать только при отсутствии.
- Streamlit AppTest и проверка сценариев в работающем интерфейсе.
- `ruff check`, `ruff format --check`, `ty`; синтаксис совместим
  с Python 3.13, runtime остаётся Python 3.14, Ruff сохраняет
  `target-version = "py313"`. Несколько типов исключений заключать в скобки.
- Crapper, Dryer и Mutator для изменённой логики.
- Обновление `.env.example`, документации доступа и журнала действий;
  небольшие последовательные коммиты.
