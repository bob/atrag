# План реализации интерфейса

Требования: [README.md](README.md). Нумерация разделов требований не является
порядком реализации. Этот план разбивает работу на проверяемые шаги.

После выполнения шага 4 от 02.11.2026 следующий шаг — **5**.
Постоянные документы и подготовленные версии разделены; состав корпуса
явно публикуется в БД и сохраняется для каждого нового хода. Прежняя история
и источники сохраняют своё происхождение. Сервис проверяет Google-идентичность
и доступ к собственным диалогам. Четыре инструмента RAG работают с сохранённым
составом, общим поиском и бюджетом, реестром источников и прежними цитатами.
Агент использует Responses API, ограничивает вызовы и передаваемую историю,
проверяет ссылки по реестру. Далее реализуются выполнение хода и восстановление.

## Порядок работы

Для каждого шага применять `ub-mode`:

1. Зафиксировать ожидаемое поведение тестом и увидеть ожидаемое падение.
   Если честный тест непрактичен, записать причину и способ проверки.
2. Внести минимальное изменение, достаточное для прохождения проверки.
3. Проверить границы данных, убрать дублирование и лишнюю сложность.
   Выполнить crapper (`CRAP < 10`), dryer (дублирование `< 0.8`) и mutator
   для затронутого кода; разобрать непокрытые участки и выжившие мутации.
4. Выполнить подходящие тесты, Ruff check/format и проверку типов изменённого
   Python-кода. Сохранить runtime Python 3.14, синтаксис Python 3.13 и `py313`.
5. Обновить журнал действий и статус шага, сохранить небольшой коммит с
   причиной, изменениями и проверкой. В конце работы отправить коммиты в `master`.

PostgreSQL проверять в существующей `atrag_test_context_20261101`:
очищать тестовые таблицы, не пересоздавать базу. Обычные тесты используют
подставные модели и не вызывают платные API.

## Шаг 1.2. Документы, версии и публикация корпуса

**Результат:** приложение получает состав доступных документов из БД.

- Разделить постоянный документ (`source_id`), неизменяемую версию материала
  (`snapshot_id`) и опубликованный состав корпуса. Идентификаторы версий
  создаёт подготовка данных; формат файла не определяет выбор документов чатом.
- Проверить нынешнюю идентичность снимка по хешу исходного файла: изменение
  подготовленных блоков, метаданных или адресов требует новой версии материала
  даже при прежнем файле. Не переписывать опубликованные материалы, на которые
  ссылаются сохранённые ходы; хеш файла и версию подготовки различать явно.
- Хранить опубликованный состав как неизменяемое соответствие
  `source_id → snapshot_id`, не более одной выбранной версии каждого документа.
  Указатель на текущий опубликованный состав хранить в БД в одном месте.
- Предоставить явную операцию публикации после успешной индексации: добавить
  документ, заменить выбранную версию либо убрать документ из текущего поиска.
  Атомарно переключать указатель на новый состав. Ошибка подготовки/индексации
  не меняет опубликованный корпус. Не определять актуальность через максимум
  `indexed_at`, время загрузки или лексикографический порядок идентификаторов.
- Проверять готовность всех включаемых версий и совместимость пространства
  embeddings. Сохранить старые опубликованные составы и материалы, на которые
  ссылаются ходы; повторная публикация того же состава идемпотентна.
- При старте нового хода сохранять ссылку на текущий состав корпуса.
  Все операции и восстановление этого хода используют сохранённый состав;
  следующий новый ход может использовать уже обновлённый корпус.
- Зафиксировать общий контракт подготовленного материала: устойчивые
  идентификаторы блоков, текст, метаданные документа/версии и типизированное
  местоположение. Для PDF это страница, для HTML — раздел/якорь,
  для DOCX — раздел/абзац. Страница и юридический адрес не обязательны для
  каждого формата. Новые загрузчики и парсеры реализуются отдельными задачами
  ingestion; этот шаг задаёт контракт и проверяет его на синтетических данных.

**Готово, когда:** опубликованы два разных документа; новая версия одного
заменяет его в составе для нового хода, сохраняя второй документ и прежние источники.
Повторная индексация старой версии не меняет выбор. Сбой и конкурирующие
публикации не оставляют смешанный состав. Обновление во время хода не меняет
его материалы, а новый ход видит обновление без изменения `.env` и перезапуска.
Пустой корпус даёт определённый результат. Материал без PDF-страниц проходит
общий контракт. Эти проверки выполняются через хранилище и операцию разрешения
состава; общий поиск проверяется в шаге 3. Миграция сохраняет ранее
проиндексированный CIRS.

Выполнен 02.11.2026: `0006_corpus_publication` сохраняет прежний CIRS,
добавляет реестр документов, неизменяемые составы и единственный указатель.
Подготовка назначает версии независимо от хеша PDF; индексация сохраняет
каждую версию отдельно, публикация явно и атомарно меняет выбранный состав.

Добавлены CLI `corpus publish`/`corpus show` и общий контракт PDF/HTML/DOCX.
Проверки: 571 тест, 100% покрытия, CRAP < 10, дублирования от 0.8 нет,
125/125 мутаций уничтожены; [журнал](ACTION_LOG.md).

## Шаг 3. Инструменты RAG и реестр источников

**Результат:** агент может безопасно получать материалы через четыре инструмента.

- Подключить `search_tax_documents`, `load_unit_text`, `load_neighbor_parts`,
  `load_context` к сохранённому для хода составу корпуса. Расширить нынешнюю
  границу поиска по одному снимку до нескольких документов, сохранив существующие
  алгоритмы ранжирования и подготовки embeddings. Получать общий top-k с учётом
  единого бюджета; не умножать лимиты на число документов.
- Передавать разрешённый состав, соединения и пользователя со стороны
  приложения; проверять аргументы модели на входе. Фильтры модели могут сузить
  поиск внутри разрешённого состава.
- Собирать реестр из фактической выдачи: стабильные номера цитат, португальские
  выдержки CIRS и оригинальные выдержки других источников, `source_id`,
  `snapshot_id`, идентификатор блока, местоположение, редакция и замечания.
- Дочитывать материал по идентичности документа, версии и блока, чтобы одинаковые
  номера статей или блоков разных документов не смешивались. Старые цитаты
  из истории разрешать по сохранённому реестру своего диалога и исходной версии.
- Ограничить одно извлечение 6000 токенов и сумму извлечений за ход 24 000.

**Готово, когда:** поиск и дочитывание возвращают ожидаемые материалы;
пустая выдача, неверные аргументы и исчерпание бюджета дают определённый
результат; модель не может расширить разрешённый состав или заменить владельца;
два документа попадают в общую выдачу, дочитываются в нужной версии и делят

фиксируется отдельно от автоматической приёмки.

## Термины хранения

- **Пользователь:** идентичность OIDC `(issuer, subject)`; email служит для допуска.
- **Документ:** логический источник с постоянным `source_id` независимо от формата.
- **Версия материала:** неизменяемый подготовленный материал с `snapshot_id`.
- **Опубликованный состав корпуса:** неизменяемый набор выбранных версий документов;
  текущий состав определяется указателем в БД.
- **Диалог:** история одного владельца.
- **Ход:** один вопрос и его выполнение с постоянным UUID, сохранённым составом
  корпуса, ответом и источниками.
- **Checkpoint:** сохранённое состояние агента внутри `thread_id` диалога.
- **Источник ответа:** фактический материал инструмента с идентичностью документа,
  версии, блока и местоположением, на который ссылается ответ.
