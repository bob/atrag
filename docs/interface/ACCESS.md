# Сервис доступа и собственных диалогов

Шаг 2 реализован в `atrag.chat`, без зависимости от Streamlit. Существующей
схемы БД достаточно; новых миграций или настроек окружения нет.

## Граница аутентификации

`ChatService.authenticate(claims, allowed_emails)` принимает claims только
от доверенного OIDC-адаптера приложения. Он должен заранее проверить подпись,
audience, срок токена и сессию. В шаге 6 этим адаптером будет нативная
аутентификация Streamlit. Словарь из URL/формы и непроверенный JWT сюда
передавать нельзя. Адаптер должен заново проверять допуск при обращении
пользователя, включая изменение конфигурационного списка разрешённых адресов.

Сервис требует Google issuer, непустой case-sensitive ASCII subject длиной
до 255 символов, email и настоящий boolean `email_verified=true`.
Два допустимых issuer — `accounts.google.com` и
`https://accounts.google.com` — приводятся к HTTPS-варианту. Адреса в claims
и списке допуска приводятся к нижнему регистру с удалением внешних пробелов;
точки и `+suffix` не преобразуются. Пустой или некорректный список закрывает
доступ. Эти поля и правила issuer/subject соответствуют
[документации Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect).

Пользователь определяется парой `(issuer, subject)`. Атомарный upsert
сохраняет UUID, дату создания и выбранный язык, обновляя подтверждённый email.
Совпадение email у разных subject не объединяет пользователей. Ошибка допуска
возвращается как `PermissionError("Access denied")`, без содержимого claims.

`User` — серверный контекст, возвращённый `authenticate`; значения этого
объекта нельзя брать из интерфейса. Сервис сопоставляет его UUID и пару
issuer/subject с БД при доступе к данным. Email и язык из устаревшего объекта
не используются для определения владельца.

## Операции

| Метод `ChatService` | Результат |
| --- | --- |
| `authenticate(claims, allowed_emails)` | Создаёт/читает пользователя после проверки допуска |
| `get_user(user)` | Читает актуальные данные пользователя и его язык |
| `set_language(user, language)` | Сохраняет `ru`, `en` или `pt`, возвращает обновлённого пользователя |
| `create_conversation(user)` | Создаёт пустой диалог с UUID и пустым заголовком |
| `list_conversations(user)` | Возвращает собственные диалоги от новых к старым |
| `get_conversation(user, conversation_id)` | Проверяет доступ и читает диалог, в том числе для восстановления из URL |
| `load_history(user, conversation_id)` | Возвращает полную историю от старых ходов к новым |
| `start_turn(user, conversation_id, turn_id, text, language)` | Проверяет владельца, сохраняет вопрос и текущий состав корпуса, возвращает состав |
| `resolve_turn_corpus(user, conversation_id, turn_id)` | После проверки владельца и принадлежности хода читает его сохранённый состав |

Методы возвращают отдельные значения `User`, `Conversation`, `Turn` и
`CorpusComposition`, которые можно использовать после закрытия соединения.
История сохраняет исходные тексты, язык каждого хода, источники, статус,
ошибку, usage и происхождение; смена предпочтения языка не переводит историю.
При равных датах порядок устойчиво определяется UUID.

Чужой или отсутствующий диалог/ход даёт одинаковый отказ в доступе.
Список диалогов содержит только записи владельца; у него может не быть записей.
Нельзя читать чужой ход через собственный диалог.

## Ход и заголовок

Первый вопрос задаёт заголовок: пробелы нормализуются, сохраняются первые
80 символов, LLM не вызывается. Исходный вопрос хранится без изменения.
Пустой или нестроковый вопрос и неподдерживаемый язык отклоняются на входе.

Создание хода и заголовка выполняется одной транзакцией с блокировкой строки
диалога. Повтор того же UUID с теми же диалогом, вопросом и языком сохраняет
один вопрос и исходный состав. Другая привязка UUID отклоняется, транзакция
откатывается вместе с возможными изменениями заголовка.

Состав выбирается только после проверки владельца. Публикация не меняет
состав существующего хода; следующий ход получает текущий состав БД.
Старый ход без сохранённого состава не получает текущий автоматически:
после проверки доступа операция сообщает об отсутствии состава.

Выполнение модели, запись результатов и восстановление checkpoints относятся
к шагам 4–5. Их будущие сервисные операции должны использовать ту же проверку
владельца перед доступом к истории, источникам или состоянию агента.
