# Чат для работы с RAG в ATRAG

Этот документ фиксирует требования. Порядок реализации и критерии готовности
каждого шага: [PLAN.md](PLAN.md).

## 1. Результат и границы первой версии

Создать приложение Streamlit для нескольких пользователей: вход через Google с настраиваемой проверкой списка разрешённых адресов, отдельные диалоги в PostgreSQL и агент LangChain, который самостоятельно вызывает инструменты RAG.

Чат работает с опубликованным корпусом документов; CIRS — первый уже проиндексированный материал. Корпус может содержать несколько документов и обновляемые версии. Интерфейс и ответы поддерживают русский, английский и португальский; цитаты сохраняют язык оригинала, для CIRS — португальский. Загрузка документов через интерфейс, просмотр исходных файлов и развёртывание сервиса в эту реализацию не входят. Расширение ingestion на новые форматы выполняется отдельными задачами; контракт корпуса и чата должен поддерживать подготовленные материалы независимо от формата файла.

Документ имеет постоянный `source_id`, подготовленная версия — внутренний `snapshot_id`. Опубликованный состав корпуса хранится в БД и выбирает не более одной версии каждого документа. После успешной индексации явная операция публикации атомарно переключает текущий состав. Время загрузки или повторной индексации не определяет актуальность редакции. Добавление документа и публикация новой версии не требуют изменения `.env` или перезапуска чата.

Каждый новый ход сохраняет текущий опубликованный состав. Выполнение и восстановление хода используют его до конца; следующий ход может получить обновлённый состав. Сохранённые источники содержат идентичность документа, версии, блока и местоположение. Старые ответы и цитаты остаются связаны с исходными материалами.

## 2. Интерфейс и доступ

- Точка входа — `streamlit_app.py`. Использовать нативные `st.chat_message`, `st.chat_input`, `st.write_stream`, `st.status` и `st.expander`.
- Боковая панель: новый диалог, список собственных диалогов, переключатель языка, сведения о составе корпуса и версиях документов, выход. Название диалога формировать из первого вопроса без дополнительного вызова LLM.
- Выбранный язык переводит подписи, статусы, ошибки и последующие ответы. Предпочтение сохраняется для пользователя; существующие сообщения не переводятся.
- При генерации показывать текст потоком и краткие этапы работы: поиск, чтение статьи, подготовка ответа. Внутренние рассуждения модели не выводить.
- В ответе использовать ссылки `[1]`, `[2]`. Под ним показывать соответствующие оригинальные выдержки, документ и версию, местоположение, редакцию и относящиеся к материалу замечания. Местоположение типизировано: страница PDF, раздел/якорь HTML, раздел/абзац DOCX. Страница и юридический адрес показываются при наличии.
- Вход реализовать через нативный [OIDC-механизм Streamlit](https://docs.streamlit.io/develop/concepts/connections/authentication). Допускать только подтверждённые Google-адреса. По умолчанию проверять список разрешённых адресов; настройка `access.check_allowed_emails = false` отключает эту проверку. Владельца определять по идентичности провайдера, а не по значению из интерфейса.
- Любое чтение диалога, отправку сообщения и восстановление состояния проверять на принадлежность текущему пользователю. Выбор диалога сохранять в URL; повторное открытие страницы восстанавливает его после проверки доступа.

## 3. Агент и инструменты RAG

Отделить бизнес-логику в пакет `atrag.chat`, независимый от Streamlit.

- Использовать `langchain.agents.create_agent` и `ChatOpenAI(model="gpt-6-luna", use_responses_api=True)`. Responses API поддерживает вызовы инструментов с выбранной моделью. [Документация модели](https://developers.openai.com/api/docs/models/gpt-6-luna), [интеграция LangChain](https://docs.langchain.com/oss/python/integrations/chat/openai).
- Подключить четыре инструмента поверх существующих сервисов: `search_tax_documents`, `load_unit_text`, `load_neighbor_parts`, `load_context`. Расширить границу поиска с одного снимка до сохранённого для хода состава корпуса, сохранив алгоритмы ранжирования и подготовки embeddings. Выдача top-k и бюджет общие для всех документов.
- Разрешённый состав корпуса, соединения и пользовательский контекст передавать инструментам со стороны приложения. Модель задаёт поисковый запрос, фильтры и необходимые адреса материалов. Фильтры сужают разрешённый поиск; дочитывание учитывает документ, версию и блок. Цитаты из истории разрешаются по реестру своего диалога и их исходным версиям.
- В системной инструкции закрепить: налоговые выводы только по полученным материалам; учитывать продолжения, исключения, примечания и отменённые положения; при недостатке данных уточнять вопрос или сообщать о пробеле. Применимость к неподтверждённому налоговому году не утверждать.
- Реестр источников формировать из фактических результатов инструментов. Проверять идентификаторы цитат; документ, версию, блок, местоположение и выдержки брать из этого реестра. Ответ с некорректными ссылками не отмечать как успешно завершённый.
- Начальные ограничения: до 8 вызовов модели и 6 инструментов за ход, до 6000 токенов на одну операцию извлечения и 24 000 суммарно за ход. Для модели: reasoning `low`, максимум 4096 выходных токенов, timeout 60 секунд, до двух повторов временных ошибок.
- Историю для LLM ограничивать бюджетом 32 000 токенов, убирая старые завершённые ходы целиком и сохраняя согласованность вызовов инструментов. Полная сохранённая история остаётся доступной в интерфейсе.

Внутренний интерфейс сервиса: `stream_turn(user, conversation_id, turn_id, text, language)` возвращает события текста, работы инструментов, завершения и ошибки. Streamlit отвечает только за их отображение.

## 4. PostgreSQL, состояние и конфигурация

- Добавить таблицы пользователей, диалогов и ходов. Хранить владельца, язык пользователя, ссылку хода на неизменяемый опубликованный состав корпуса, тексты сообщений, источники, статусы выполнения и usage модели/embeddings. Диалог не привязывать к единственному снимку.
- Хранить реестр документов, их подготовленные версии и опубликованные составы в БД. Проверять готовность версий, совместимость пространства embeddings и единственность выбранной версии документа. Публикация идемпотентна; старые составы и материалы, используемые ходами, сохраняются.
- Состояние агента сохранять через `PostgresSaver`; `thread_id` соответствует диалогу. Session State использовать для состояния интерфейса.
- Каждому ходу назначать постоянный UUID. Повторное выполнение страницы не должно добавлять сообщение или запускать модель повторно.
- Выполнение в одном диалоге сериализовать PostgreSQL advisory lock. При сбое сохранять незавершённый статус; продолжение запускать только явной кнопкой, с последнего checkpoint и без повторного добавления вопроса.
- Кешировать общие клиенты и пулы соединений через `st.cache_resource`. Пользовательские сообщения и результаты не помещать в общий кеш.
- Добавить зависимости Streamlit с поддержкой auth, LangChain, LangChain OpenAI и LangGraph; обновить lock-файл.
- Сохранить существующий механизм `.env` для OpenAI и PostgreSQL; добавить настройку модели чата. Состав корпуса и идентификаторы документов/версий задаются данными БД. Google OIDC и список разрешённых адресов задавать через Streamlit secrets; предоставить шаблон без секретов.
- Таблицы приложения создавать миграцией Alembic, таблицы checkpoints — явным шагом команды миграции. Открытие интерфейса миграции не выполняет.
- Документировать настройку Google callback, миграции и запуск командой `uv run streamlit run streamlit_app.py`.

## 5. Проверки и критерии готовности

- **Агент:** поиск, последовательное дочитывание, продолжение разговора, пустая выдача, некорректные аргументы, ограничения бюджета, timeout и ошибки OpenAI.
- **Корпус:** два документа в общей выдаче, публикация новой версии, повторная индексация старой версии, ошибки и конкурирующие публикации, пустой корпус. Обновление корпуса во время выполнения не меняет материалы хода и его восстановления; следующий ход видит новый состав без изменения `.env`.
- **Источники:** корректные ссылки, версии и местоположение; отсутствие выдуманных цитат; сохранение замечаний и признаков неполного текста. Старые цитаты продолжают разрешаться после обновления. Синтетический источник без PDF-страниц проходит поиск, дочитывание и цитирование.
- **Предметные сценарии:** резидентство, исключения статьи 16(4), переходные примечания, связь 68-A → 68 с таблицами, известный пробел статьи 100 и вопрос вне корпуса.
- **Доступ и сохранение:** два пользователя не видят чужие диалоги; история восстанавливается после перезапуска; обновление страницы и две вкладки не дублируют ход.
- **Streamlit AppTest:** экран входа, отказ в доступе, создание и переключение диалогов, три локали, источники и восстановление после ошибки. В обычных тестах использовать подставную модель без платных запросов.
- PostgreSQL-тесты выполнять в существующей `atrag_test_context_20261101`, очищая тестовые таблицы без пересоздания базы.
- Проверить изменённые Python-файлы через `ruff check`, `ruff format --check` и проверку типов. Сохранить runtime Python 3.14, синтаксис Python 3.13 и Ruff target `py313`.
- Завершить проверкой работающего Streamlit с подставной моделью. Живую проверку Google и OpenAI выполнять отдельно с настроенными учётными данными и согласованными API-вызовами.

## 6. Настройка базового каркаса

Шаг 1 подготавливает зависимости, настройки и хранилище. Экран входа,
выполнение агента и `streamlit_app.py` относятся к последующим шагам
[плана](PLAN.md). Пересмотр 02.11.2026 добавляет обязательные шаги 1.1–1.2
перед доступом и агентом: исправление каркаса и публикацию состава корпуса.

```sh
uv sync --locked
uv run atrag config check
uv run atrag db migrate
```

В существующий `.env` можно добавить:

```dotenv
ATRAG_CHAT_MODEL=gpt-6-luna
```

Значения окружения процесса имеют приоритет над `.env`.
`config check` проверяет настройки, не открывая соединение с БД.

Диалог создаётся без выбора документа или версии. Миграция
`0005_chat_provenance` поверх опубликованной `0004_chat` переносит прежний
`chat_conversations.snapshot_id` в `chat_turns.legacy_snapshot_id` каждого
существующего хода, затем удаляет столбец диалога. Пользователи, история,
источники, статусы и usage сохраняются. Внешний ключ сохраняет связь со старым
материалом. У новых ходов `legacy_snapshot_id` пуст: это только происхождение
старых данных, а не настройка поиска или ссылка на текущий состав корпуса.
Идентификаторы документов и версий в `.env` не нужны.
Миграция `0006_corpus_publication` добавляет реестр `source_documents`,
неизменяемые опубликованные составы `corpus_releases`/`corpus_members`,
единственный указатель `corpus_state` и `chat_turns.corpus_release_id`.
Существующий CIRS и его идентификаторы сохраняются. Текущий состав после
обновления пуст: миграция не выбирает редакции за оператора.

Термины:

- `source_id` — постоянная идентичность документа, общая для его редакций.
- `source_sha256` / `raw_snapshot_id` — хеш исходного файла и адрес ранних
  PDF-артефактов подготовки; он не выбирает материалы чата.
- `snapshot_id` — хеш подготовленного пакета с версией подготовки, метаданными,
  блоками, адресами, отчётами и пространством embeddings. В БД его отдельно
  фиксирует `preparation_sha256`; у прежних строк это поле пустое.
- `release_id` — хеш соответствия `source_id → snapshot_id`, независимый от
  порядка документов. Состав может быть пустым.

`ingest package` пишет формат 2: `snapshot_id` подготовленной версии,
`raw_snapshot_id` файла и `preparation_version`. Чтение пакетов формата 1
поддерживается и назначает подготовленную идентичность, не переписывая пакет.
`ingest index` возвращает идентификатор подготовленной версии и устанавливает
её один раз. Другая подготовка того же PDF создаёт другую версию; старые
строки сохраняются. Метаданные берутся из актуального реестра при подготовке,
а первый манифест сырых байтов не перезаписывается.

После индексации создать JSON с изменениями, например:

```json
{"pt-at-cirs": "<snapshot_id из результата ingest index>"}
```

```sh
uv run atrag corpus publish --changes corpus-changes.json
uv run atrag corpus show
uv run atrag corpus show --release <release_id>
```

Ключ добавляет документ или заменяет его версию; значение `null` убирает
документ из следующего состава. Остальные документы сохраняются. Перед
переключением проверяются наличие индекса, принадлежность версии документу
и общее пространство embeddings. `needs_review` сохраняет замечания и не
равнозначен сбою индексации. Публикации сериализуются блокировкой единственной
строки указателя; состав и указатель записываются одной транзакцией. Повтор
того же состава возвращает тот же ID. Триггеры запрещают изменение состава
и материалов, использованных опубликованным составом или прежними ходами.

Внутренние операции `atrag.corpus` принимают соединение/engine от сервиса:
`start_turn` сохраняет текущий состав вместе с новым UUID хода,
`resolve_turn_corpus` возвращает только сохранённый состав, `resolve_corpus`
читает текущий или явно названный состав. Повтор UUID сохраняет прежнее
происхождение и отвергает подмену запроса. Проверка владельца относится к
сервису шага 2 и должна выполняться до этих операций. У исторических ходов
`corpus_release_id` остаётся пустым: текущий корпус им не приписывается.

`atrag.schemas.materials.PreparedMaterial` задаёт общий контракт: постоянный
документ, хеш файла, версию подготовки, JSON-метаданные и блоки с уникальным
устойчивым `block_id`, текстом и типизированным местоположением. PDF содержит
страницу, HTML — якорь и необязательный раздел, DOCX — абзац и необязательный
раздел. Юридический адрес не обязателен. HTML/DOCX проверены синтетически;
их загрузчики и общий поиск добавляются отдельно.

`atrag db migrate` применяет Alembic до `0006_corpus_publication`, затем явно вызывает
`PostgresSaver.setup()` на отдельном autocommit-соединении. Оно нужно для
`CREATE INDEX CONCURRENTLY`. Оба этапа защищены одной сессионной advisory lock;
ожидающие миграции проверяют её без открытой транзакции, чтобы не блокировать
построение индексов. При сбое второго этапа первый остаётся применённым, а повторная команда
завершает настройку. Открытие будущего интерфейса не выполняет миграций.
Откат `0006_corpus_publication` отказывается удалять подготовленные версии
или сохранённые составы ходов. Без таких данных он восстанавливает прежнюю
схему; публикация без привязанных ходов при осознанном откате удаляется.
Откат `0005_chat_provenance` восстанавливает прежнюю схему только когда у каждого
диалога есть ходы и у всех его ходов известен один и тот же прежний снимок.
При пустом диалоге, неизвестном снимке или разных версиях откат отказывается
менять данные. Перед удалением чата через откат `0004_chat` нужно явно решить,
что делать с такой историей. При откате `0004_chat` удаляются данные чата;
корпус и таблицы checkpoints не затрагиваются. Такая операция предназначена
только для осознанного отката.

Для будущего Google OIDC скопировать отслеживаемый шаблон:

```sh
cp .streamlit/secrets.toml.example .streamlit/secrets.toml
```

Локальный `.streamlit/secrets.toml` игнорируется Git. В Google Auth Platform
создать OAuth-клиент типа Web application и добавить точный redirect URI
`http://localhost:8501/oauth2callback`. Для другого порта/адреса одинаково
изменить URI у клиента Google и в secrets. Заполнить `auth.google.client_id`,
`auth.google.client_secret`, задать случайный длинный `auth.cookie_secret`
и перечислить допустимые адреса в `access.allowed_emails`. Если приложение
Google находится в режиме Testing, также добавить их в Test users.
Формат auth и callback соответствует
[официальной инструкции Streamlit](https://docs.streamlit.io/develop/tutorials/authentication/google).
Проверки Google-идентичности, `email_verified` и политики доступа выполняются
на каждом rerun. Чтобы разрешить вход всем пользователям с подтверждённым
Google-адресом, в локальном `.streamlit/secrets.toml` задайте:

```toml
[access]
check_allowed_emails = false
```

В этом режиме `allowed_emails` игнорируется и может отсутствовать.
Настройка принимает только булевы `true` и `false`, без кавычек. Если она
отсутствует или равна `true`, вход разрешён только адресам из `allowed_emails`;
пустой список запрещает вход всем. Перезапустите приложение после изменения
secrets. Ограничения Test users самого OAuth-приложения Google задаются отдельно.

После реализации шага 6 приложение запускается командой:

```sh
uv run streamlit run streamlit_app.py
```
