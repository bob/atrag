# Шаг 1: общие контракты PDF и HTML-коллекции

Выполнен 07.11.2026 в ветке `faq-ingestion-plan`. Следующий этап — Шаг 2.

## Контракты и термины

| Термин | Представление и инвариант |
| --- | --- |
| Формат источника | `SourceDefinition.source_format`: `pdf` либо `html_collection`, независимо от `document_type`. `SourceFormat.snapshot_filename` задаёт имя входа снимка в одном месте |
| Источник FAQ | `data/sources/faq.json`: `pt-at-faq`, язык `pt`, издатель AT, HTTPS URL всего каталога. Даты получения и хеш будущего обхода не выдумываются |
| Страница коллекции | `HTMLPage`: исходный URL, относительный `.html`-файл, SHA-256 исходных байтов, размер, конечный URL, время с часовым поясом, HTTP 200, заголовки и тематическая навигация |
| Полный manifest коллекции | `HTMLCollection`: каталог присутствует, URL и пути уникальны, каждый навигационный адрес представлен страницей. Неуспешные получения должны остаться в отчёте fetch и блокировать создание такого полного manifest |
| Идентичность коллекции | SHA-256 отсортированного по URL массива `{url, sha256}`; JSON UTF-8, `sort_keys=True`, `separators=(",", ":")`, `ensure_ascii=False`, как в Шаге 0. Размер — сумма исходных байтов HTML. Время, конечный URL, заголовки, имена локальных файлов и порядок обхода не входят в хеш |
| Снимок HTML | `SourceSnapshot` схемы 2 с `collection`; путь `raw/<source_sha256>/collection.json`. Хеш, общий размер и URL каталога сверяются с manifest. Подготовленная идентичность по-прежнему задаётся `preparation_sha256` |
| Запись FAQ | `FAQEntry`: полный исходный вопрос и ответ, тематический путь, опубликованный номер, URL страницы, якорь, исходные и абсолютные ссылки, порядковая позиция |
| Постоянный ID FAQ | `entry_id=<ключ страницы>:<номер>`, например `faqs-00267:3286`; `legal_unit_id=<instrument_id>:<entry_id>`, например `pt-at-faq:faqs-00267:3286`. Позиция и якорь не меняют ID. Один номер на разных страницах даёт разные ID |
| Единица FAQ | `LegalUnit` с областью `faq`, ролью `at_explanation`, видом `document`, `topic` или `faq_entry`. Только `faq_entry` содержит метаданные вопроса. Юридические адреса, нормативный статус, PDF-страницы/локаторы и редакционные поправки запрещены |
| HTML-местоположение | `HTMLLocation.page_url` — необязательное поле для прежних материалов, обязательное для FAQ-единицы. URL страницы не содержит фрагмента; якорь хранится отдельно и сверяется с FAQ-метаданными |

Файлы manifest описывают проверяемый сохранённый вход. Проверка фактических
байтов и получение полного снимка относятся к Шагу 2. Контракт не заменяет
проверку HTTP и хешей файлов. Fetch, HTML-парсер, FAQ chunk/package/index,
маршрутизация и интерфейс в этом этапе не реализуются.

## Совместимость CIRS и БД

При отсутствии значений новые `collection`, `faq`, `page_url` не попадают
в сериализацию. Формат `pdf` также не добавляется в старые сериализованные
источники. Поэтому прежние хеши подготовленных артефактов не меняются.
`tests/fixtures/cirs/legacy-contracts.json` фиксирует источник, реальный manifest
CIRS и статью 16 вместе с хешами сериализации, снятыми до изменения моделей.
Повторное чтение и сериализация сохраняют эти хеши; существующие проверки
пакетов v1/v2 сохраняют идентичность, PDF-сигнатуру, размер и происхождение.
PDF import явно отклоняет реестр HTML-коллекции.

Миграция `0010_faq_contracts` добавляет только необходимые изменения:
`source_snapshots.source_format` с default `pdf` и ограниченным доменом,
область `faq`, виды `topic`/`faq_entry` и роль `at_explanation` в обеих таблицах
единиц и фрагментов. Метаданные и URL помещаются в существующий JSONB payload;
дополнительные столбцы для каждого поля FAQ не нужны. Nullable PDF-страницы
уже поддерживаются миграцией 0007.

Upgrade сохраняет строки, payload, векторы и идентичности существующего CIRS,
повторный запуск не меняет результат. Downgrade возможен для прежнего PDF-корпуса
и отказывается терять HTML-происхождение либо FAQ-единицы. Проверки используют
существующую БД `atrag_test_context_20261101`, очищая тестовые таблицы между
сценариями. База не пересоздаётся. Рабочая БД и опубликованный корпус не менялись.

Эквивалентная мутация меняет `ensure_ascii=False` на `True` в хеше коллекции.
Сериализованные `HttpUrl` используют ASCII (IDNA-хосты и percent-encoding),
а SHA-256 допускает только `[0-9a-f]`. Поэтому массив идентичности целиком
ASCII и оба режима дают одинаковые байты для всех допустимых входов.
Параметр оставлен явным, чтобы формула соответствовала Шагу 0.
