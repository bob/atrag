# Шаг 3: извлечение и проверка FAQ

Выполнен 07.11.2026 в ветке `faq-ingestion-plan`. Следующий этап — Шаг 4:
общие chunk/embed/package/index. Проверка этого этапа выполняется полностью
на сохранённом снимке Шага 2.

## Результат

Чистая функция `parse_faq_page(raw, page_url, topic_path)` возвращает
типизированные FAQ, таблицы и объяснения ошибок. Она использует уже
закреплённый в `uv.lock` BeautifulSoup 4.15.0 с `html.parser`; новых зависимостей
нет. Все заголовки ищутся по DOM целиком: это сохраняет 34 вопроса, вышедших
из контейнера `faqAccordion` из-за повреждённой разметки исходного сайта.

Вопрос связывается с собственным ответом через `aria-controls`/`href` и
обратный `aria-labelledby`. Начальное состояние collapse не влияет на
извлечение. Постоянный `entry_id` составлен из ключа фактически полученной
страницы и опубликованного номера AT; порядок хранится отдельно в `ordinal`.
Конфликты внутри страницы и между страницами коллекции требуют проверки.
Меню, футер и служебные данные вне ответа исключены.

`ExtractedFAQ` содержит исходные вопрос и ответ, отдельные нормализованные
тексты, путь темы из заголовка навигации страницы, фактический URL, якорь
заголовка, ссылки, элементы списков, ID таблиц и текстовые отсылки. Абзацы,
переносы и пункты сохраняются в порядке DOM; у пунктов дополнительно есть
признак упорядоченного списка и глубина вложенности. Отсылки к CIRS/CIVA и
другим актам остаются текстовыми упоминаниями и не становятся адресом FAQ.

Общий `ExtractedTable` параметризован видом части. PDF по умолчанию сохраняет
прежний `TablePart`, HTML использует `HTMLTablePart` с HTML-местоположением,
ячейками и `rowspan`/`colspan`. PDF-поля отсутствуют у HTML. Поддержаны все
18 обнаруженных таблиц, включая таблицы с объединениями и одноячеечную
таблицу с существенным текстом. `verified` для таблицы означает сохранённые
DOM-ячейки и объединения, а не юридическую проверку её содержания.

Изображения и другие неподдержанные значимые элементы, неверные объединения,
вложенные/пустые таблицы, пустой ответ, неверная связь, отсутствующий номер,
конфликт ID, отсутствие темы и несоответствие количества заголовков/ответов
дают `needs_review`. Отчёт сохраняет URL, позицию и объяснение; потери не
остаются молчаливыми. Неизвестный шаблон отклоняется также при проверке
снимка. Успешное выполнение команды с `needs_review` сохраняет диагностические
артефакты, но не разрешает готовность версии к публикации.

## Воспроизведение

```sh
ATRAG_DATA_DIR=data/faq-step2-20261107 uv run atrag ingest extract \
  --registry data/sources/faq.json \
  --source data/faq-step2-20261107/saved-input
```

Можно передать `raw/<source_sha256>/collection.json` вместо `saved-input`.
Команда проверяет manifest, хеши и размер каждого исходного файла до записи
результатов. Каждый запуск имеет отдельную директорию `runs/<run_id>`:

| Файл | Содержимое |
| --- | --- |
| `faqs.jsonl` | Полные типизированные записи `ExtractedFAQ` |
| `tables.json` | Общие таблицы с HTML-частями |
| `report.json` | Количества до/после, отклонённые позиции, ошибки по страницам, конфликты ID, таблицы, ссылки и отсылки |
| `manifest.json` | Состояние попытки, версия парсера, DOM-зависимость, snapshot_id и SHA-256 выходных файлов |

Каталог с исходными HTML и полные результаты остаются вне Git.
[extraction-verification.json](extraction-verification.json) фиксирует
независимую сверку с инвентаризацией Шага 0 и хеши результата.
