# Шаг 2: получение и сохранение полного снимка FAQ

Выполнен 07.11.2026 в ветке `faq-ingestion-plan`. Следующий этап — Шаг 3,
извлечение вопросов и ответов. Для этого этапа достаточно сохранённого HTML:
повторный сетевой обход каталога для разработки и проверок не нужен.

## Результат

Добавлена команда `ingest fetch --registry data/sources/faq.json`. Она обходит
только тематическую навигацию официального FAQ и сохраняет исходные HTML-байты,
SHA-256, размер, время получения, запрошенный и конечный URL, HTTP-статус,
заголовки и связи страниц. Ссылки внутри ответов не расширяют обход.

Нормализуются относительные ссылки, фрагменты и подтверждённые HTTP/Pages
алиасы; query-параметры сохраняются. Переадресации проверяются перед каждым
следующим запросом. Чужой хост, другая область сайта, нестандартный порт,
userinfo и неизвестное продолжение пагинации не обходятся. Неподдержанное
продолжение навигации блокирует завершение.

Получение ограничено тремя одновременными запросами, таймаутом HTTP 30 секунд,
тремя попытками при transport error, 429 или 5xx и пятью переходами redirect.
Задержка повторов — 1/2 секунды либо `Retry-After`, ограниченный 30 секундами.
Ответы 206, неверный Content-Type, пустой/неизвестный шаблон и HTML-страница
ошибки при статусе 200 отклоняются. Лимит 1000 страниц блокирует бесконечную
пагинацию и требует проверки состояния.

## Сохранение и возобновление

| Артефакт | Назначение |
| --- | --- |
| `fetch/<fetch_id>/state.json` | Явная контрольная точка: реестр источника, полученные страницы и ошибки; незавершённая очередь восстанавливается из сохранённых связей |
| `fetch/<fetch_id>/.lock` | Неблокирующий OS-lock одного владельца; после завершения процесса владение освобождается, оставшийся файл не мешает возобновлению |
| `fetch/<fetch_id>/html/*.html` | Полученные байты; файлы и состояние записываются через временный файл и атомарную замену одним владельцем |
| `runs/<run_id>/manifest.json` | Отдельная попытка, её fetch_id, терминальный статус и идентичность полного снимка; Ctrl+C также записывается как неуспех |
| `raw/<source_sha256>/collection.json`, `manifest.json`, `html/*.html` | Только полный проверенный снимок, опубликованный атомарным переименованием staging-директории |

Возобновление проверяет исходный реестр, хеши/размеры уже сохранённых файлов,
границы URL и соответствие связей исходному HTML до сетевых запросов.
Успешные страницы повторно не запрашиваются. Ошибки остаются в контрольной
точке и блокируют публикацию. Повторное получение тех же байтов и конкурентная
публикация сохраняют первый полный снимок и его происхождение.

`ingest snapshot` теперь принимает сохранённый HTML-manifest либо его каталог
через `--source`. `ingest inspect` для HTML проверяет файлы и навигацию,
записывает отчёт шаблонов и количества номерных заголовков. Он не извлекает
ответы и оставляет `review_status=needs_review`. PDF-команды CIRS продолжают
работать по прежнему пути.

## Проверка полного сохранённого входа

По уточнению пользователя дополнительные сетевые обходы не выполняются.
Новый сетевой запуск остановлен sandbox до получения HTML; повторный запуск
вне sandbox не был разрешён. Все дальнейшие проверки использовали сохранённый
обход Шага 0 и `httpx.MockTransport`.

Весь вход один раз прогнан через новый fetch как локальный HTTP replay:
151 подставной ответ, 0 сетевых запросов, замкнутая навигация. Отдельно исходные
файлы импортированы через настоящий CLI `snapshot/inspect` с сохранением
первоначальных времён получения, конечных URL и заголовков Шага 0.
Времена replay не выдаются за новое получение официального сайта.

| Показатель | Значение |
| --- | --- |
| Каталог / тематические страницы | 1 / 150 |
| Номерные заголовки вопросов | 1630, включая карточки за пределами повреждённого `faqAccordion` |
| Исходные HTML-байты | 11 645 100; совпадают с Шагом 0 |
| Снимок | `8773a9e3f191d0c9ec88ac25326497fc3cdeeb6973338c3acae6f98b65bc277d` |
| Каталог снимка | `data/faq-step2-20261107/raw/<source_sha256>/` |
| Отчёт CLI inspect | `data/faq-step2-20261107/runs/3c7bdc53-35f8-4188-bd31-c84247c18788/report.json` |

Хеш отличается от разведочного хеша Шага 0 только из-за согласования алиаса
каталога: `Pages/faqs.aspx` теперь совпадает с реестром и контрактом снимка,
а разведка использовала `pages/faqs.aspx`. Формула хеша сохранена; байты HTML
не изменены. Повторная обработка сохранённого входа даёт ту же идентичность.

Полные HTML и локальные отчёты остаются вне Git. В репозиторий входят код,
тесты, lockfile и эта инструкция.

## Команды без сети для следующего этапа

```sh
export ATRAG_DATA_DIR=data/faq-step2-20261107

.venv/bin/atrag ingest snapshot --registry data/sources/faq.json \
  --source data/faq-step2-20261107/saved-input

.venv/bin/atrag ingest inspect --registry data/sources/faq.json \
  --source data/faq-step2-20261107/saved-input
```

Вместо `saved-input` можно передать `raw/<source_sha256>/collection.json`.
Эти команды не создают HTTP-клиент и проверяют фактические сохранённые файлы.
Будущее явно запрошенное обновление выполняется через `ingest fetch`; его
прерванный запуск продолжается той же командой с `--resume <fetch_id>`.
Идентификатор и ошибки доступны в `fetch/<fetch_id>/state.json` и manifest
соответствующей попытки. Для Шага 3 обновление не требуется.
