# План ingestion FAQ Portal das Finanças

Дата: 06.11.2026. Статус: план подготовлен; реализация и загрузка корпуса ещё не выполнялись.

Цель: подготовить FAQ Autoridade Tributária e Aduaneira и включить их в опубликованный корпус вместе с CIRS. Пользователь задаёт вопрос в существующем интерфейсе; общий поиск находит релевантные выдержки обоих источников, а ответ показывает проверяемые цитаты и кликабельные ссылки на PDF CIRS и конкретные тематические страницы FAQ.

## 1. Объём задачи и проверенные исходные данные

Начальная точка — [каталог Questões Frequentes](https://info.portaldasfinancas.gov.pt/pt/apoio_contribuinte/questoes_frequentes/Pages/faqs.aspx). Он содержит ссылки на тематические страницы разных разделов, включая IRS и IVA. В объём входит весь FAQ-каталог, доступный через его тематическую навигацию. Ограничивать загрузку разделом IRS не требуется.

Проверка сайта 06.11.2026 установила:

- На [странице Residentes/Incidência Pessoal](https://info.portaldasfinancas.gov.pt/pt/apoio_contribuinte/questoes_frequentes/pages/faqs-00267.aspx) вопросы и ответы уже находятся в HTML, внутри `#faqAccordion`. Для проверенного образца браузерный рендеринг при извлечении не нужен.
- У вопроса есть видимый номер: например, `3286`. Его HTML-адрес — `#collapse20`, связанный с заголовком `#heading20`. Номер позиции в accordion не подходит для постоянного ID вопроса.
- Встречается сложная вложенная HTML-разметка внутри ответа. Извлечение должно сохранять абзацы, перечисления и условия, а не просто удалять теги регулярным выражением.
- [FAQ по режиму освобождения IVA](https://info.portaldasfinancas.gov.pt/pt/apoio_contribuinte/questoes_frequentes/pages/faqs-00720.aspx) ссылаются на CIVA. Упомянутый кодекс не превращает FAQ в статью этого кодекса.
- В HTML проверенного образца `rel=canonical` использует HTTP и порт 80, хотя получение по HTTPS работает. Канонизацию нужно проверять по фактическому URL, а не слепо принимать этот тег.

Это разведка нескольких страниц, а не подтверждение полноты всего каталога. Полная инвентаризация — первый этап реализации.

Под «тем же пайплайном, что у CIRS» понимается:

```text
получение → неизменяемый снимок → извлечение → структура и проверка
→ части с контекстом → embeddings и кеш → проверенный переносимый пакет
→ атомарная индексация → публикация CIRS + FAQ → общий RAG и ссылки в интерфейсе
```

Для HTML используется собственный извлекатель; PDF/OCR-этапы CIRS остаются адаптером своего формата. Исходные тексты сохраняются на португальском; поиск и интерфейс проверяются на en/pt/uk/ru. Ссылки из ответов FAQ сохраняются как ссылки; рекурсивная загрузка упомянутых законов, PDF и внешних сайтов в эту задачу не входит. Автоматическое обновление по расписанию и определение юридической применимости по налоговым годам — отдельные задачи.

## 2. Что переиспользуется и что нужно изменить

Основание — текущий код, а не только исторический [план CIRS](../document-ingestion/README.md) и [план интерфейса](../interface/PLAN.md).

| Область | Текущее состояние | Работа для FAQ |
| --- | --- | --- |
| Источник | `SourceDefinition` уже допускает `document_type="faq"` | Добавить реестр FAQ и явный формат исходных данных |
| Снимок и пакет | `SourceSnapshot`, `services/snapshots.py`, `services/packages.py`, `services/index.py` требуют `source.pdf` и PDF-сигнатуру | Поддержать снимок HTML-коллекции и его проверяемые файлы |
| Единицы и части | `LegalUnit` и `chunk.py` используют области CIRS, юридические виды единиц и PDF-локаторы | Представить FAQ собственной семантикой; переиспользовать общее разбиение и проверки |
| Местоположение | Есть `HTMLLocation(section, anchor)` и возможность отсутствия PDF-страниц | Добавить URL конкретной страницы внутри коллекции |
| Векторизация и БД | Есть кеш, переносимые embeddings, транзакционный индекс | Использовать тот же сервис и пространство embeddings |
| Корпус и RAG | `corpus.py`, `retrieval/corpus.py`, `RagService` уже поддерживают несколько источников | Проверить на настоящем HTML-пакете и смешанных запросах |
| Точные адреса | `normalize_address()` ищет упоминание статьи внутри всей строки и вводит фильтр `document_scope="code"` | Различить самостоятельный точный адрес и смысловой вопрос с упоминанием статьи |
| Источники ответа | `chat/db/sources.py` сохраняет выдержки и местоположение; UI показывает подписи | Добавить URL в серверный реестр цитат и кликабельные ссылки обоих форматов |

Общий контракт материала уже есть в `schemas/materials.py`; его нужно согласовать с реальным ingestion. Второй независимый индекс, отдельный FAQ-поиск и отдельный чат не нужны.

## 3. Форма данных и инварианты

### 3.1. Источник и снимок коллекции

- Один постоянный источник: `source_id="pt-at-faq"`, `document_type="faq"`, издатель AT, язык `pt`, исходный URL каталога. CIRS сохраняет `pt-at-cirs`.
- Одна версия FAQ охватывает полный зафиксированный обход каталога. Новый состав корпуса содержит обе пары: `pt-at-cirs → выбранный CIRS`, `pt-at-faq → выбранный FAQ`.
- Снимок содержит HTML каталога, тематических страниц и manifest с соответствием URL → файл → SHA-256, связями навигации и результатами получения. Время получения, конечный URL и HTTP-метаданные сохраняются как происхождение.
- `source_sha256` коллекции вычисляется по канонически упорядоченному составу URL и хешей исходных байтов. Время получения и порядок обхода не входят в идентичность. `snapshot_id` подготовленной версии учитывает исходные данные, парсер, разбиение и подготовленные артефакты по существующим правилам.
- Повторная обработка одного сохранённого входа детерминирована. Новый сетевой обход может получить другие исходные байты, даже при одинаковом видимом тексте; совпадающие embedding inputs переиспользуют кеш.
- Неполученная обязательная страница, неизвестный шаблон или необъяснённая потеря вопросов блокируют готовность новой версии. Предыдущая опубликованная версия остаётся доступна.

### 3.2. Вопрос, ответ и местоположение

На границе HTML-парсера ввести типизированную запись FAQ:

| Поле | Смысл |
| --- | --- |
| `entry_id` | Стабильная пара ключа тематической страницы и опубликованного номера FAQ; например, `faqs-00267:3286` |
| `faq_id` | Номер вопроса AT, сохранённый отдельно от номера позиции |
| `question`, `answer` | Полные оригинальные тексты; нормализация хранится отдельно |
| `topic_path` | Категория и подкатегории из навигации |
| `page_url`, `anchor` | URL страницы и фактически найденный якорь в этом снимке |
| `links` | Ссылки из ответа с исходным текстом и разрешёнными абсолютными URL |
| `ordinal` | Порядок внутри страницы; не участвует в постоянном ID вопроса |

Не предполагать глобальную уникальность номера FAQ по всему сайту. Повторные навигационные ссылки на одну страницу объединяются; совпадение текста разных вопросов не является основанием терять их происхождение. Отсутствующий или конфликтующий номер требует явного решения в отчёте проверки, а не ID, зависящего от позиции.

Общая структура: коллекция → тема → FAQ. Наименьшее изменение существующего контракта единицы материала (`LegalUnit`): добавить явные виды `topic`/`faq_entry`, область `faq`, роль разъяснения AT и типизированные FAQ-метаданные. Для FAQ юридические поля `code/article/paragraph/subparagraph` отсутствуют; ссылки на статьи хранятся отдельно как отсылки. Валидация запрещает сочетание FAQ с выдуманным юридическим адресом.

У FAQ `page_start/page_end=None`, пустые PDF-локаторы и типизированный `HTMLLocation` с URL страницы, разделом и якорем. Для коллекции одного `source_url` каталога недостаточно. Новые необязательные поля не должны менять сериализацию и хеши старых PDF-артефактов при отсутствии значения.

### 3.3. Части, пакет и цитаты

- Базовая поисковая единица — вопрос вместе с ответом. В embedding input входят название источника, тематический путь, номер, вопрос и соответствующая часть ответа.
- Длинный ответ делится существующим механизмом точных диапазонов. Вопрос и необходимые вводные условия повторяются как контекст; исходные срезы позволяют без потерь восстановить полный текст. Разные FAQ не склеиваются в одну часть.
- Списки, таблицы, примечания и ссылки сохраняют смысловую структуру. Данные HTML не получают фиктивных PDF-координат. Неподдержанная значимая таблица или изображение попадает в проверку и блокирует `ready` до разрешения.
- Новый формат пакета описывает тип и состав исходных файлов явно. Чтение существующих пакетов CIRS версий 1/2 сохраняется; HTML использует новую версию схемы. Проверяются хеши всех файлов, отношения единиц/частей, покрытие, токены и полное соответствие embeddings.
- Ссылка цитаты строится сервером из проверенных метаданных того же документа и снимка. Для FAQ — тематическая страница с проверенным якорем, для CIRS — официальный PDF и физическая страница `#page=N`.
- Текст выдержки, версия и URL сохраняются вместе. URL живого сайта не является неизменяемым архивом: старый ответ продолжает показывать сохранённую выдержку своего снимка.

## 4. First Make it Work: последовательность реализации

Каждый этап начинается с теста наблюдаемого поведения, его ожидаемого падения и минимального исправления. Затем проверяется результат этапа; следующий этап начинается после прохождения его условий.

### Шаг 0. Зафиксировать примеры, полноту и эталон поиска

1. Снять полный список тематических URL из каталога и промежуточной навигации. Проверить повторные ссылки, вложенные страницы, пагинацию и варианты шаблона; записать точные количества страниц и вопросов после обхода.
2. Вручную разобрать один вопрос от HTML до записи FAQ и ссылки. На этой проверенной записи строить парсер.
3. Сохранить небольшие исходные HTML-fixtures и ожидаемые записи: IRS, другой налог, длинный ответ, сложные списки, ссылки и обнаруженные таблицы. Полный crawl хранить вне Git, как остальные данные корпуса.
4. До изменения retrieval зафиксировать набор запросов и ожидаемые единицы: отдельные CIRS, отдельные FAQ и пересечение тем. Включить смысловой вопрос с упоминанием статьи и самостоятельный точный адрес.

**Готово, когда:** есть проверенный пример, инвентаризация шаблонов, правила полноты и эталон, не подобранный под будущую выдачу.

### Шаг 1. Поддержать HTML-коллекцию в общих контрактах

1. Тестами показать, что FAQ без PDF и юридического адреса проходит общий контракт, получает устойчивую идентичность и сохраняет URL страницы.
2. Расширить источник, снимок, единицы и местоположение по разделу 3. Оставить форматные решения в одном месте; не выводить формат из `document_type`.
3. Проверить совместимость сохранённых пакетов/артефактов CIRS: прежние идентичности, чтение, ссылки и правила PDF. Подготовить миграцию только для реально необходимых изменений БД.

**Готово, когда:** оба формата представлены без фиктивных значений; неправильные сочетания отклоняются; старый CIRS читается с прежней идентичностью.

### Шаг 2. Получать и сохранять полный снимок FAQ

1. Добавить отдельное получение HTML-коллекции через CLI, например `ingest fetch --registry data/sources/faq.json`. Это новая команда, пока не существующая инструкция запуска.
2. Обходить только тематическую навигацию FAQ на официальном хосте; обычные ссылки в ответах не расширяют границы обхода. Нормализовать относительные URL, фрагменты и подтверждённые алиасы страниц, сохраняя значимые параметры пагинации.
3. Задать таймауты, ограниченные повторы с задержкой и небольшой предел параллельных HTTP-запросов. Проверять статус, тип содержимого и фактический шаблон: ответ 200 со страницей ошибки не считается FAQ.
4. Сохранять исходные байты и manifest через staging с атомарным завершением. Возобновлять прерванное получение по явно сохранённому состоянию; файл состояния одного запуска имеет одного владельца.
5. Подключить снимок к существующим `snapshot/inspect` через адаптер HTML, сохранив работу CIRS CLI.

**Проверки:** повторные ссылки, перенаправление, таймаут/429/5xx, прерванная загрузка, неизвестный шаблон, неполный обход. Повторная подготовка сохранённого снимка не обращается к сети.

### Шаг 3. Извлекать и проверять FAQ

1. Реализовать чистый HTML-парсер по fixtures с DOM-парсером, сохраняющим порядок блоков; выбрать одну необходимую зависимость и закрепить lockfile.
2. По структуре accordion связывать вопрос с его собственным ответом, независимо от вложенных тегов и начального свёрнутого состояния.
3. Сохранять вопрос, ответ, тему, ссылки и фактическое местоположение; исключать меню, футер и SharePoint-служебный текст.
4. Поддержать обнаруженные HTML-таблицы в общем контракте таблиц без обязательных PDF-полей. Значимые неподдержанные элементы выводить в отчёт проверки до публикации.
5. Формировать отчёт: страницы и вопросы до/после разбора, пустые ответы, конфликты ID, исключения, таблицы и отсылки. Для каждой потери должно быть проверяемое объяснение.

**Готово, когда:** ожидаемые вопросы и полные ответы совпадают с ручными образцами; ни один обнаруженный вопрос не потерян молча; перестановка вопросов не меняет их постоянные ID.

### Шаг 4. Пройти общие chunk/embed/package/index

1. Отделить в существующем chunker правила выбора единиц и формирования контекста CIRS от общих диапазонов, токенизации и сборки частей. Для FAQ кандидаты — `faq_entry`.
2. Устранить безусловные `min/max` по PDF-локаторам и жёсткий словарь областей CIRS на общем пути. Не копировать chunker целиком для HTML.
3. Использовать те же лимиты частей, embedding API, пакетирование запросов и PostgreSQL-кеш. Пространство брать у опубликованного CIRS; FAQ должно точно совпадать по модели и размерности. Текущий проверенный ориентир — `text-embedding-3-large` / 1536; перед живым запуском проверить фактические параметры выбранного CIRS.
4. Расширить сборку, загрузку и установку исходников пакета на HTML-коллекцию. Все проверки выполнить до записи в корпус; индексация остаётся транзакционной.
5. Добавить воспроизводимый локальный сценарий CLI от сохранённого HTML до проиндексированного FAQ-пакета. Первую проверку выполнить с подставным embedding API.

**Готово, когда:** повторный запуск не создаёт дубликатов; полный ответ собирается из частей; кеш переиспользуется; испорченный файл и неполные векторы отклоняются; сбой индексации сохраняет предыдущие данные. Настоящий FAQ-пакет проходит тот же импорт, что CIRS, без HTML-парсера на сервере.

### Шаг 5. Проверить общий поиск и публикацию

1. Через существующий `corpus publish --changes` добавить FAQ, сохранив выбранный CIRS и остальные документы. Индексация сама по себе не публикует источник.
2. Оставить общие query embedding, ранжирование, top-k и бюджет контекста в `search_corpus`; `source_ids` продолжает сужать состав сохранённого хода.
3. Разделить точный запрос адреса (`CIRS 16`, `artigo 16 do CIRS`) и смысловой вопрос, содержащий такой адрес. Последний должен искать и FAQ; голая отсылка остаётся точным поиском нормы. Воспроизвести текущую потерю FAQ тестом до изменения `normalize_address()` и обоих путей поиска.
4. Проверить `load_unit_text`, `load_neighbor_parts`, `load_context` на FAQ: исходный ответ и его части читаются, отсутствующие юридические связи не выдумываются. Междокументное автоматическое разрешение всех отсылок не является условием этой задачи.
5. Обновление FAQ во время хода не меняет его состав. Новый ход получает новую версию; старые цитаты и восстановление продолжают читать старую. Откат выбора FAQ не изменяет CIRS.

**Готово, когда:** запрос по общей теме возвращает релевантные CIRS и FAQ через существующий RAG-инструмент; точный адрес не путается с упоминанием закона внутри разъяснения; публикация и откат атомарны.

### Шаг 6. Показать ссылки обоих источников в интерфейсе

1. Расширить серверную запись цитаты URL и типом источника, сохранив адрес `source_id/snapshot_id/block_id`, номер, оригинальную выдержку и границы. Ссылка берётся из данных, использованных в этом ходе.
2. В существующей карточке источника показать кликабельный переход нативным элементом Streamlit, название, тип «CIRS / FAQ AT», тему и номер вопроса либо PDF-страницу. Добавить подписи на en/pt/uk/ru.
3. Для FAQ проверить переход к видимому заголовку вопроса. Наличие `#collapseNN` ещё не гарантирует раскрытие ответа; использовать проверенный якорь заголовка, а при отсутствии работающего якоря — URL страницы с номером вопроса в подписи.
4. Для CIRS проверить связь официального URL с используемым снимком: текущий реестр помечает его `candidate`. Если удалённый PDF отличается, сохранить честную отметку происхождения и версию выдержки; не объявлять текущий файл идентичным старому снимку.
5. Сохранить чтение истории, где URL ещё отсутствует. Не подставлять в старые FAQ-цитаты URL или якорь из новой версии.
6. В правилах ответа сохранить различие закона и разъяснения AT. На смешанных эталонных вопросах ответ использует оба релевантных источника и цитирует их. Номера цитат ссылаются только на фактически полученные выдержки.

**Готово, когда:** в одном ответе по подходящему вопросу доступны две рабочие ссылки — CIRS и FAQ; повторное открытие истории сохраняет ссылки, выдержки и версии. Само наличие двух источников в корпусе не требует добавлять нерелевантную цитату в каждый ответ.

## 5. Then Make it Right: приёмка и устранение причин

### Автоматические проверки

- **Парсер:** проверенные HTML-fixtures; полный текст и ссылки; исключение служебного текста; перестановка, повторные номера, пустой ответ, неизвестный шаблон и таблицы.
- **Подготовка:** точные диапазоны, восстановление длинного ответа, лимиты с учётом повторяемого вопроса, отсутствие смешения FAQ, идентичность сохранённого входа и совместимость старых CIRS-пакетов.
- **PostgreSQL:** настоящий импорт двух пакетов, кеш, повторный импорт, откат транзакции, несовместимые embeddings, полнота публикации, обновление FAQ и сохранённые ходы. Использовать `atrag_test_context_20261101`; очищать тестовые таблицы между запусками, не пересоздавать базу.
- **RAG и UI:** один ранжированный список по двум источникам, фильтр источника, точные и смысловые запросы со статьёй, дочитывание FAQ, серверные URL, последовательные citation IDs, история и локализации.
- **Streamlit:** постоянные проверки через `AppTest`, проверка реального локального runtime через agent API по skill developing-with-streamlit. Переходы по официальным URL и фактические HTML-якоря проверить в браузере отдельно.

### Качество настоящего поиска

Зафиксировать минимум 12 смысловых сценариев: 4 CIRS, 4 FAQ и 4 смешанных; подготовить эквиваленты на en/pt/uk/ru. Например, тема резидентства связывает FAQ `3286` и положения статьи 16 CIRS; точные целевые единицы и выдержки сверить при подготовке эталона.

Для каждого сценария заранее сохранить ожидаемые идентификаторы и обязательные условия ответа. На этом фиксированном наборе каждый ожидаемый источник должен присутствовать в top-5; для смешанных случаев обязательны оба источника. Отдельно проверить, что итоговый ответ цитирует оба и что кликабельные URL соответствуют именно процитированным данным. Прежний benchmark CIRS должен сохранить свои пороги; синтетические векторы не подтверждают смысловое качество.

Перед полной векторизацией посчитать страницы, вопросы, части, токены, попадания кеша и оценку стоимости по актуальному тарифу. Выполнить короткую живую проверку, затем подготовить полный FAQ в том же embedding-пространстве. Сохранить реальный usage, задержку и результаты; не смешивать синтетические и настоящие пакеты.

Если приёмка падает, сначала воспроизвести конкретную причину: потеря текста, неверное разбиение, фильтр адреса, бюджет или ранжирование. Не маскировать проблему квотой на два источника или добавлением ссылок, для которых нет полученной выдержки.

### Проверки ub-mode

Для изменённого Python-кода: `ruff check`, `ruff format --check`, совместимость синтаксиса с Python 3.13 при runtime Python 3.14 и сохранённом `target-version="py313"`. Несколько типов исключений всегда заключать в скобки.

После поведенческих проверок использовать существующие `tools/ub-mode/crapper`, `dryer`, `mutator`: CRAP каждой изменённой функции < 10; устранить дублирование с рейтингом ≥ 0.8; покрыть пропуски и уничтожить выжившие значимые мутации. Эквивалентные мутации разбирать с объяснением. Проверять изменённые области и непосредственно затронутые общие функции; результаты сохранять в журнале.
