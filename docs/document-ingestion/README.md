# План подготовки налоговых документов для RAG

Статус: реализованы Шаги 1–2 раздела 5 — настройки, регистрация источника и неизменяемый снимок. Первый источник: [CIRS.pdf](../CIRS.pdf). Доступны `config check` и `ingest snapshot`; остальные этапы, `db migrate` и `search` описывают будущую реализацию. Запуск готовых команд описан в [README проекта](../../README.md).

Цель: получить из португальского оригинала проверяемый, версионируемый корпус в PostgreSQL с pgvector, пригодный для поиска по смыслу, точным обозначениям и периоду применимости нормы.

Стек проекта: Python, LangGraph, Streamlit, OpenAI API, PostgreSQL и pgvector. Здесь проектируем загрузку, извлечение, структурирование, embeddings, индексацию и проверку поиска. Чат в Streamlit и LangGraph-агент, вызывающий поисковый инструмент, относятся ко второй части. Для неё первая часть предоставляет общий поисковый сервис и сведения об ограничениях корпуса.

Решение от 30.10.2026: основным хранилищем проекта выбран PostgreSQL. Модель связанных источников, норм и редакций хранится в таблицах; pgvector обеспечивает поиск по embeddings, встроенный полнотекстовый поиск PostgreSQL дополняет его. Это решение заменяет первоначальный выбор Weaviate.

## 2. Правила корпуса

1. **Португальский оригинал является основным текстом.** Хранить исходный PDF и извлечённые фрагменты на `pt`. Поддержать вопросы на русском (`ru`), английском (`en`) и португальском (`pt`); использовать единую модель мультиязычных embeddings. Переводы не заменяют оригинал и не требуют отдельных копий корпуса. Качество проверяется на одинаковых по смыслу запросах на всех трёх языках.
2. **Границы определяются структурой документа.** Для кодекса: акт → глава → раздел → статья → номерной пункт (`número`) → подпункт (`alínea`). Для FAQ: вопрос вместе с полным ответом. Короткую статью можно индексировать целиком; длинную делить по пунктам.
3. **Фрагмент сохраняет условия применения.** В него входят заголовок, вводная часть родительского пункта, исключения, оговорки и редакционные примечания, относящиеся к этому положению. Связанные положения доступны через идентификаторы; непроверенная автоматическая сводка не заменяет текст нормы.
4. **Источник и его тип сохраняются до ответа пользователю.** Закон, инструкция AT, индивидуальное разъяснение и FAQ не становятся взаимозаменяемыми фрагментами после индексации.
5. **История корпуса сохраняется.** Новая редакция не перезаписывает старую. Период действия и налоговый период устанавливаются по подтверждающим источникам, а не по дате скачивания.
6. **Поиск сочетает векторы, полнотекстовый поиск и точные SQL-фильтры.** Обозначение статьи обрабатывается как структурированный адрес. Семантическая похожесть не должна подменять указанный кодекс или редакцию.

## 3. Модель данных до написания парсера

Использовать четыре связанные сущности. Это проектные термины, которые затем должны совпадать с именами моделей в коде.

| Сущность | Назначение |
| --- | --- |
| `SourceSnapshot` | Неизменяемые байты конкретного документа, происхождение и даты получения |
| `LegalUnit` | Устойчивый адрес статьи, пункта, подпункта или пары FAQ независимо от редакции |
| `NormVersion` | Текст конкретной редакции единицы, юридический статус и подтверждённая применимость |
| `SearchFragment` | Единица индексации с контекстом, вектором и ссылками на первые три сущности |

Основное хранилище этих сущностей - таблицы PostgreSQL: `source_snapshots`, `legal_units`, `norm_versions`, `search_fragments`. Их связи, ссылки между нормами, локаторы в снимках и принадлежность фрагментов выпускам задавать внешними ключами и таблицами связей. Embeddings и их кеш хранить в PostgreSQL с pgvector. PDF остаются неизменяемыми файлами или объектами; JSON/JSONL служат промежуточными артефактами, экспортом и материалом для проверки, а не параллельным источником истины после загрузки в базу.

Выпуски описывать в `corpus_releases`, их состав - в `release_fragments`, активный выпуск - в `corpus_state`. Неизменившиеся фрагменты и векторы использовать повторно между выпусками через связи. Происхождение и страницы каждого вхождения фрагмента сохранять отдельно со ссылкой на снимок. Первичные ключи, ограничения уникальности и проверки допустимых значений закрепить миграциями.

### Библиотеки и взаимодействие с БД

Набор согласован с пользователем 30.10.2026. На Шаге 1 версии закреплены в `uv.lock`; установка и интеграционные тесты прошли на Python 3.14.6 с локальным PostgreSQL 16.13 и серверным pgvector 0.8.7. Миграции схемы корпуса относятся к последующей реализации.

| Библиотека / пакет | Роль |
| --- | --- |
| [SQLAlchemy 2.x](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#psycopg) | Типизированные ORM-модели таблиц, запросы, транзакции и пул соединений |
| [Psycopg 3](https://www.psycopg.org/psycopg3/docs/basic/install.html), пакет `psycopg[binary,pool]` | Драйвер PostgreSQL; поддержка отдельного пула для checkpointer |
| [pgvector для Python](https://github.com/pgvector/pgvector-python), пакет `pgvector` | Тип вектора и операции поиска в SQLAlchemy; серверное расширение `vector` устанавливается отдельно |
| [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html) | Миграции схемы, ограничений и индексов; включение расширения `vector` |
| [langgraph-checkpoint-postgres](https://docs.langchain.com/oss/python/langgraph/add-memory#use-in-production) | `PostgresSaver` для сохранения и восстановления состояния графа в служебных таблицах |
| [python-dotenv](https://bbc2.github.io/python-dotenv/) | Единая загрузка настроек из `.env` |

- Для первой версии выбрать синхронный доступ. `db.py` создаёт SQLAlchemy Engine и фабрику сессий; пул соединений переиспользуется внутри процесса. Каждая операция получает собственную сессию, которая закрывается после завершения. Между потоками и пользователями Streamlit изменяемая сессия не разделяется, согласно [правилам SQLAlchemy](https://docs.sqlalchemy.org/en/21/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks).
- Доступ к корпусу оформить узкими функциями сохранения снимка, загрузки фрагментов, поиска и публикации выпуска. Обычные операции используют ORM; FTS, векторный поиск и RRF - SQLAlchemy Core либо параметризованный SQL. Парсер и правила формирования фрагментов остаются чистыми преобразованиями данных.
- Для пакетной загрузки использовать уникальные ключи и `INSERT ... ON CONFLICT`. Границы транзакций задавать явно для пакета записи и переключения активного выпуска; вызовы OpenAI выполнять вне транзакций БД.
- Checkpointer подключается через собственный Psycopg-пул к той же базе и отдельным служебным таблицам. Не накладывать пул Psycopg на пул SQLAlchemy: это два независимых потребителя с ограниченным суммарным числом соединений.
- Сохранить один канонический `DATABASE_URL` вида `postgresql://...` для приложения, миграций и checkpointer. В `db.py` для SQLAlchemy строить объект URL с явно выбранным драйвером `postgresql+psycopg`; `PostgresSaver` получает исходный PostgreSQL DSN. Не заводить второй адрес базы и не собирать строки подключения вручную.
- Схему корпуса изменять через проверенные миграции Alembic; автогенерацию просматривать вручную. Инициализация служебных таблиц LangGraph остаётся отдельной частью команды настройки базы, описанной в шаге 9.

| Текст | `text_original`, `text_normalized`, `embedding_text`, `context_unit_ids`, `references`, `editorial_notes`, `tables` |
| Локатор | `page_start`, `page_end` как физические страницы PDF с нумерацией от 1; `printed_page_labels`, координаты исходных блоков |
| Качество | `extraction_method`, `review_status`, обнаруженные пропуски, неопределённые ссылки и проблемы таблиц |
| Воспроизводимость | `corpus_release_id`, `schema_version`, `parser_version`, `chunker_version`, `embedding_model`, `embedding_dimensions`, `embedding_input_hash`, `fragment_id` |

Неизвестные значения явно остаются неизвестными. Например, у локального CIRS `downloaded_at` неизвестен; фактическое время импорта записывается в `ingested_at` в UTC. Общая дата обновления сборника не подставляется во все `revision_publication_date`. У FAQ адрес статьи может отсутствовать: обязательность полей зависит от типа документа.

Адреса должны различать, например:

```text
pt:CIRS:art:16:n:1:al:a
pt:CIRS:art:68-A
pt:DL:442-A/1988:art:1
pt:CIRS:art:1
```

`article` хранить строкой: `68-A`, а не числом. `references` содержат исходное обозначение, распознанный акт/статью и статус разрешения. Ссылка на другой кодекс не превращается в ссылку на одноимённую статью CIRS. Разрешение ссылки на редакцию происходит с учётом периода запроса.

## 4. Версионирование и применимость

Разделить три независимые оси:

- **Снимок источника:** что именно скачали и когда узнали об этом документе.
- **Редакция нормы:** когда текст вступил в силу, изменился или был отменён.
- **Применимость:** к каким доходам, налоговым годам, событиям и переходным ситуациям относится положение.

`effective_from`/`effective_to` описывают полуоткрытый интервал `[from, to)`. `effective_to_open=true` означает подтверждённое отсутствие установленной конечной даты, а не пропущенную дату. `validity_status` принимает `unknown`, `confirmed` или `conditional`. Список `applicable_tax_years` содержит только проверенные годы; пустой список не означает «любой год». Сложные переходные условия остаются в `application_conditions` и требуют отдельного решения, если зависят от обстоятельств налогоплательщика.

Для вопроса о доходах за 2024 год:

1. Поисковый сервис получает `tax_year=2024`; при необходимости отдельно получает дату события. Год подачи декларации не заменяет год дохода.
2. Отбирает подтверждённые применимые редакции из опубликованного выпуска корпуса. Интервал действия сам по себе не заменяет проверку налогового периода: возможны переходные и ретроактивные положения.
3. При нескольких изменениях внутри года возвращает редакции с их условиями; не выбирает одну только по более поздней публикации.
4. Если покрытие 2024 года не подтверждено, возвращает `coverage_gap`, а не молча использует сборник 2026 года. Условные нормы выделяются отдельно и не выдаются как безусловно применимые.

Для исторического покрытия понадобятся официальные редакции соответствующего периода, изменяющие акты и переходные положения. Их загрузка и юридическая сверка - отдельный проверяемый этап. Один текущий PDF достаточен для разработки извлечения и поиска, но не для обещания корректного исторического ответа.

В манифесте выпуска хранить матрицу покрытия по акту, положениям и налоговому году, известные пробелы и ссылки на доказательства. Совпадение текста в двух снимках позволяет повторно использовать embedding, но не доказывает непрерывность действия нормы между ними.

### Шаг 2. Неизменяемый снимок

Выполнен 30.10.2026: модель `SourceSnapshot` в `src/atrag/ingestion/models.py`, импорт в `src/atrag/ingestion/snapshots.py` и команда `uv run atrag ingest snapshot [--registry путь.json]`. Импорт локальный, без БД и OpenAI; исходник не изменяется. SHA-256 служит `snapshot_id`, а UUID попытки записывается отдельно в `data/runs/<run_id>/manifest.json`.

Манифест `data/raw/<sha256>/manifest.json` сохраняет размер, относительный путь к копии, `ingested_at` в UTC и первоначальный реестр в поле `source`. Неизвестные даты остаются `null`, URL сохраняет исходный статус. Повторная попытка проверяет целостность и переиспользует первый снимок; её происхождение записывается в журнале попытки, в том числе при другом реестре с теми же байтами. Каталог с PDF и манифестом публикуется атомарным переименованием; конкурирующие попытки используют один снимок. Повреждение или неполный существующий снимок останавливают импорт без перезаписи. В журнале фиксируются успешные и неудачные попытки; аварийное завершение процесса может оставить статус `running`.

- Импортировать `docs/CIRS.pdf` без изменения исходника. Для будущего скачивания проверять домен, HTTP-статус, MIME и сигнатуру PDF, ограничивать размер и время ожидания.
- Сохранить копию в `data/raw/<sha256>/source.pdf` и манифест с происхождением, контрольной суммой и фактическими датами. При повторном импорте тех же байтов использовать существующий снимок.
- Отдельный `run_id` идентифицирует попытку исполнения. Не включать время запуска в идентификатор снимка или ключ кеша.

### Шаг 3. Извлечение с сохранением расположения

- Первым адаптером попробовать `pdfplumber`: страницы, блоки, координаты, таблицы. Для диагностики использовать Poppler (`pdfinfo`, `pdftotext`, `pdftoppm`). Результат сохранять до нормализации.
- Текстовый слой есть, но это не гарантирует полноту: проверять изображения, таблицы, пустые области и подозрительно короткие страницы. Для таблицы 68-A предусмотреть OCR области изображения с португальским языком и ручную сверку чисел по рендеру.
- Склеивать таблицу статьи 68 через разрыв страниц; сохранять заголовки колонок, единицы, строки и связь с пунктом. Не превращать проценты и денежные диапазоны в набор несвязанных чисел.
- Удалять повторяющиеся колонтитулы и печатные номера из поискового текста, сохраняя их в происхождении. Исправлять переносы строк и слов осторожно: не терять отрицания, буквенные суффиксы, десятичные запятые и обозначения `n.º`/`alínea`.
- Получить `pages.jsonl` с исходными блоками, нормализованным текстом, таблицами, способом извлечения и локаторами.

### Шаг 4. Разбор юридической структуры

- Сначала вручную разметить небольшой образец: статьи 1 и 16 обоих актов, CIRS 2-A, 68, 68-A и отменённый пункт. По нему проверить правила парсера.
- Отличать заголовки статей от упоминаний внутри текста и строк оглавления; использовать расположение и контекст, а не одно регулярное выражение.
- Разделять вводный декрет и кодекс, главы, разделы, статьи, пункты и подпункты. Поддержать продолжение положения через страницу и ненумерованную статью.
- Привязать примечания об изменениях/отмене к соответствующему положению. Преамбулу, редакционные примечания и переходные нормы сохранять с явной ролью; не считать их обычными действующими статьями CIRS.
- Извлечь отсылки, включая «предыдущий пункт» и «следующая статья»; неоднозначные ссылки оставить неразрешёнными с исходным текстом. Не скачивать все упомянутые документы автоматически.

### Шаг 5. Проверка редакций и периодов

- По примечаниям выделить кандидатов на изменяющие акты; подтвердить даты и условия по официальным источникам, включая Diário da República. LLM может предложить разметку, но не является источником юридической даты.
- Сохранить редакцию каждого изменённого положения и доказательства применимости. Дочерний пункт наследует период родителя только при наличии основания; смешанные редакции внутри статьи допустимы.
- Отменённый текст не удалять из истории; пометить статус и подтверждённые периоды. Не выдавать отметку `Revogado` за содержательное действующее правило.
- Неустановленные периоды и спорные таблицы направлять на проверку. Они могут сохраняться как исследовательские данные, но исключаются из результатов с подтверждённой применимостью.

### Шаг 6. Формирование фрагментов

- Основной фрагмент - полный номерной пункт с его подпунктами; короткая статья без пунктов остаётся целой. Для длинного пункта дробить по подпунктам, повторяя вводное условие и прикрепляя связанные исключения.
- Цель около 700 токенов, верхняя рабочая граница около 1200 с учётом контекста. Если юридически связный блок не помещается, разбивать по смысловым границам с явными связями либо отправлять на разметку; молча обрезать текст нельзя.
- `text_original` сохраняет португальскую формулировку; `embedding_text` добавляет название кодекса, область акта, статью, заголовок и необходимый родительский контекст. Даты загрузки и технические идентификаторы в embedding не включать.
- Глобальное перекрытие соседних статей не применять. Полный текст статьи хранить для расширения контекста по `parent_id`; извлечённые условия и исключения проверять отдельно. Для FAQ вопрос и ответ не разрывать.
- Получить `fragments.jsonl` и отчёт: количество статей/пунктов, длины, непокрытые блоки, проблемы структуры, таблиц и ссылок.

### Шаг 7. Embeddings через OpenAI API

Для первого измерения использовать `text-embedding-3-small`, 1536 измерений; `text-embedding-3-large` оставить кандидатом для сравнения на наборе запросов на русском, английском и португальском. Это стартовая гипотеза, а не утверждение о достаточном качестве. Мультиязычная поддержка и размерность описаны в [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/embeddings).

- Вычислять векторы в приложении и сохранять их в PostgreSQL через pgvector. Так модель, повторные попытки и кеш контролируются в одном месте.
- Перед запросом проверять непустой ввод и ограничения выбранной модели по токенам и размеру пакета. Проверять соответствие числа, порядка и размерности ответов входным фрагментам.
- Кешировать в таблице embeddings с уникальным ключом `(model, dimensions, embedding_input_hash)`, отдельно от версии нормы и времени запуска. Фрагменты ссылаются на сохранённые векторы. Повторный импорт не должен заново оплачивать уже сохранённые векторы.
- Для временных ошибок использовать ограниченные повторные попытки с задержкой и jitter; ошибки авторизации и данных останавливают этап. Сохранять результаты успешных пакетов и расход токенов.
- Документы и запросы векторизовать одной моделью, размерностью и согласованной схемой подготовки текста. Смена модели требует отдельного пространства embeddings и переиндексации. Проверять совместимость размерности с типом pgvector и выбранным индексом; векторы разных моделей не смешивать даже при одинаковой размерности.

### Шаг 8. PostgreSQL, pgvector и гибридный поиск

Создать миграции реляционной схемы и включить расширение `vector`. Для стартовой модели использовать `vector(1536)`, для полнотекстового индекса - `tsvector` и GIN. Гибридный поиск объединяет два списка кандидатов через Reciprocal Rank Fusion (RRF), а не складывает несопоставимые исходные оценки. Такой подход описан в [документации pgvector](https://github.com/pgvector/pgvector#hybrid-search). Стандартное ранжирование PostgreSQL FTS отличается от BM25.

- Из `text_normalized`, `unit_title` и `document_title` формировать взвешенный `tsvector` с португальской конфигурацией. Проверить нормализацию и стоп-слова на юридических формулировках. Использовать `tsquery` и `ts_rank_cd` согласно [документации PostgreSQL FTS](https://www.postgresql.org/docs/current/textsearch-controls.html).
- Идентификаторы, кодекс, область акта, номер статьи, тип документа и статусы хранить в типизированных колонках с подходящими SQL-индексами. Точные обозначения искать по этим колонкам, независимо от полнотекстовой нормализации.
- Даты хранить как `date`, моменты загрузки как `timestamptz`, годы как целые числа; применимые годы связывать с редакциями норм. Для гибких дополнительных данных использовать `jsonb`, но поля фильтрации и связи не прятать в непрозрачную JSON-строку.
- Для точного запроса нормализовать `artigo 53.º CIVA`, `art. 53 CIVA`, `CIVA 53` в `(code=CIVA, article=53)`. Сначала применять фильтр адреса и периода. Если загружен только CIRS, сообщить об отсутствии CIVA, даже если в CIRS есть статья с тем же номером.
- Для смыслового запроса сначала выделить допустимые по выпуску, периоду и подтверждённости фрагменты. На небольшом корпусе выполнять точный поиск по косинусному расстоянию и полнотекстовый поиск среди этого набора; объединять ранги через RRF и затем выбирать результаты.
- HNSW добавлять после измерений. При приближённом поиске фильтрация может уменьшать число найденных кандидатов; проверить iterative scans, полноту результатов и план SQL-запроса. Особенности описаны в [документации pgvector о фильтрах](https://github.com/pgvector/pgvector#filtering).
- Для русских и английских запросов не рассчитывать на совпадение слов с португальским текстом в FTS. Сначала измерить мультиязычный векторный поиск; при необходимости добавить португальскую поисковую формулировку, сохраняя точные обозначения и исходный вопрос на любом из поддерживаемых языков. Перевод запроса не изменяет корпус.
- Один и тот же набор обязательных SQL-фильтров использовать в обеих ветвях поиска. После объединения добавлять родительские условия/исключения и разрешённые ссылки из того же выпуска и применимой редакции; контролировать бюджет контекста.

### Шаг 9. Повторный запуск и публикация

- Сначала выполнить и проверить этапы как обычные функции; затем связать их последовательным `StateGraph`. Состояние содержит `run_id`, `snapshot_id`, `corpus_release_id`, пути к артефактам, счётчики и ошибки, а не все байты PDF и векторы.
- Checkpoints LangGraph сохранять в той же PostgreSQL через `PostgresSaver` из `langgraph-checkpoint-postgres`, с отдельными служебными таблицами. Инициализацию checkpointer выполнять отдельным шагом настройки согласно [документации LangGraph](https://docs.langchain.com/oss/python/langgraph/add-memory#use-in-production). На каждом этапе сохранять проверяемый артефакт. Возобновление может повторить узел, поэтому внешние записи должны оставаться идемпотентными.
- До начала записи создать стабильный `corpus_release_id` из версий входных снимков, схемы, обработки, её параметров, проверенных метаданных, модели embeddings и размерности. `fragment_id` детерминированно получать из редакции нормы, версии/параметров разбиения и содержимого с контекстом, без идентификатора выпуска. При повторе проверять содержимое и использовать ограничения уникальности и идемпотентные вставки.
- Разные запуски используют собственные каталоги. Запись одного подготовленного выпуска сериализовать advisory lock PostgreSQL на выделенном соединении; транзакции записи делать короткими и не удерживать их во время вызовов OpenAI. Механизм блокировки описан в [документации PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS). Будущие Streamlit-сессии не разделяют изменяемое состояние запуска.
- Новый выпуск имеет статус подготовки; его состав записывается в `release_fragments` транзакциями по пакетам. Обычный поиск выбирает только состав активного опубликованного выпуска. Общие фрагменты и embeddings неизменяемы и используются по ссылкам; ошибки пакета не публикуют частичный результат.
- После проверки количества, идентификаторов, метаданных, размерности и поисковых примеров одной транзакцией блокировать строку `corpus_state`, проверять готовность выпуска, отмечать публикацию и менять ссылку на активный выпуск. Откат меняет эту ссылку на ранее проверенный выпуск. Запись в базе является единственным источником активного состояния; файловые манифесты остаются экспортом.
- Поисковый сервис читает активный `corpus_release_id` из PostgreSQL один раз в начале запроса и закрепляет его для обеих ветвей поиска и расширения контекста. Старые выпуски сохраняются для отката. Ошибка загрузки оставляет действующий выпуск доступным.

## 6. Граница со второй частью: контракт поиска

Реализовать и проверить сервис независимо от Streamlit и затем обернуть его инструментом LangGraph:

```text
search_tax_documents(query, tax_year, event_date=None, document_types=None, limit=5, query_language=None)
```

`tax_year` обязателен для поиска норм с подтверждённой применимостью. Если период вопроса неизвестен, будущий чат уточняет его; текущую дату нельзя незаметно подставлять вместо периода дохода.

`query_language` принимает `ru`, `en` или `pt`; набор поддерживаемых языков определить в одном общем типе. Язык можно указать явно; иначе определять его на входной границе. Для коротких обозначений вроде `CIRS 16`, где определение ненадёжно, приложение передаёт язык интерфейса. Язык вопроса не используется как фильтр языка исходных документов: английский и русский вопросы должны находить португальские нормы.

Во второй части пользователь сможет выбрать язык ответа: русский, английский или португальский. По умолчанию чат отвечает на языке вопроса, а явный выбор языка ответа имеет приоритет. Поисковый сервис возвращает оригинальные португальские фрагменты; чат может объяснять их на выбранном языке, сохраняя оригинальные цитаты, обозначения актов и ссылки.

Результат содержит:

- `status`: `ok`, `needs_period`, `coverage_gap` или `no_match`; `corpus_release_id`, установленный `query_language` и описание проверенного покрытия;
- найденные португальские фрагменты с оценками, типом источника, актом/статьёй/пунктом, редакцией, периодом, условиями, URL и страницами;
- обязательный родительский контекст, исключения, ссылки и отдельно выделенные условные кандидаты/неразрешённые вопросы.

Будущий ответ должен отдельно называть законодательное основание, позицию AT, индивидуальное разъяснение и FAQ. Поле `document_type` определяет представление источника, а не заменяет проверку содержания и применимости. Конфликты источников возвращаются явно; высокий поисковый score не делает FAQ законом и не распространяет индивидуальное разъяснение на любой случай.

## 7. Порядок реализации и проверки

Каждый этап завершать отдельным проверяемым результатом. Для поведения сначала написать тест, увидеть ожидаемое падение и затем сделать минимальную реализацию. На страницах CIRS сначала вручную получить эталон, затем сравнивать парсер с ним.

| Этап | Результат | Проверка перед переходом дальше |
| --- | --- | --- |
| 1. Настройки и модели | `.env.example`, типы, миграции PostgreSQL и реестр источника | Приоритет окружения, подключение и расширение pgvector, ограничения схемы, разные адреса двух актов |
| 2. Снимок и извлечение | PDF, манифест, `pages.jsonl` | SHA-256, физические/печатные страницы, сохранение оригинала, распознавание пропущенной таблицы 68-A |
| 3. Структура | `legal_units.jsonl` | Оглавление не создаёт дубликаты; различаются декрет/CIRS, `2`/`2-A`, пункты, отмена, переходы страниц |
| 4. Редакции | `norm_versions.jsonl`, карта покрытия | Неизвестные даты не выдумываются; границы интервалов, переходные условия, два изменения за год |
| 5. Фрагменты | `fragments.jsonl`, отчёт качества | Родительские условия, отрицания, исключения, ссылки и обе части таблицы 68 сохранены |
| 6. Векторизация | Кеш и отчёт использования API | Проверка входа/выхода, повтор пакета после сбоя; повторный импорт использует кеш |
| 7. Индексация | Подготовленный выпуск в PostgreSQL с pgvector и FTS | Пакетная ошибка откатывает пакет и не публикует неполный выпуск; повтор не создаёт дубликаты, неизменившиеся фрагменты используются повторно |
| 8. Поиск и публикация | Сервис, активный выпуск и отчёт оценки | Точные/смысловые/исторические запросы на `ru`, `en`, `pt`, изоляция выпусков, атомарная публикация при конкурирующих запусках, возобновление, откат |

Подготовить небольшой эталонный набор с ожидаемыми `legal_unit_id`, редакциями и обязательным контекстом:

- тройки русских/английских/португальских вопросов о теме статьи 16 без указания номера, например «Как определяется налоговое резидентство в Португалии?», «How is tax residency determined in Portugal?», «Como se determina a residência fiscal em Portugal?»; ожидаемые положения и обязательный контекст совпадают;
- явный выбор языка, определение языка полного вопроса и короткое обозначение с языком интерфейса; английский вопрос находит документ с `language=pt`;
- точные варианты обозначения CIRS 16, CIRS 68-A и CIVA 53; последний даёт `coverage_gap` при корпусе только CIRS;
- пункт с исключением и отсылкой: результат содержит необходимые связанные положения, а не только удобную цитату;
- таблица 68 с продолжением и таблица 68-A после OCR: строки и столбцы совпадают с ручным эталоном;
- запрос за 2024 год при наличии только этого PDF: нет неподтверждённой подмены редакцией 2026 года;
- тот же запрос после добавления проверенных исторических источников: возвращается редакция для 2024 года;
- отменённое положение, неизвестный период, условное переходное правило и отсутствующий документ;
- FAQ и индивидуальное разъяснение: вопрос/ответ и тип источника не теряются.

Для всех трёх языков повторить случаи с исключениями и налоговым периодом: смена языка не меняет применимую редакцию и не скрывает `coverage_gap`. При реализации чата отдельно проверить ответ на английском и приоритет явно выбранного языка ответа.

Для тестов истории на уровне модели использовать явно синтетические редакции, а для приёмки реального корпуса - подтверждённые официальные документы. Синтетический тест не доказывает юридическое покрытие 2024 года.

Предлагаемые критерии MVP: точные адресные запросы и фильтрация периода проходят весь эталонный набор; для смысловых запросов целевая доля попаданий ожидаемого положения в top-5 не ниже 90% отдельно для русского, английского и португальского. Отдельно измерять полноту обязательного контекста, корректность цитат, задержку и расход токенов. Сравнить vector-only, PostgreSQL FTS и hybrid с RRF; параметры выбирать по результатам, а не по предположению, что hybrid всегда лучше. При добавлении HNSW сравнить выдачу с точным поиском на тех же SQL-фильтрах.

Модульные проверки парсера и поиска не требуют сети. Интеграционные проверки PostgreSQL/pgvector выполнять в отдельной тестовой базе с теми же миграциями; проверять ограничения, откат транзакций, конкурирующую публикацию и восстановление checkpoints. Настоящий вызов OpenAI - отдельная небольшая проверка с настроенным ключом. После появления кода применять `crapper`, `dryer` и `mutator` из `tools/ub-mode`: снижать CRAP ниже 10, устранять дублирование с рейтингом от 0.8, проверять выжившие мутации и удалять мёртвый код.

## 8. Предлагаемая структура реализации

```text
src/atrag/
  settings.py                # единственная точка чтения .env и окружения
  db.py                      # SQLAlchemy Engine, фабрика сессий и адаптация DATABASE_URL
  db_models.py               # типизированные ORM-модели таблиц корпуса
  ingestion/
    models.py                # снимок, юридическая единица, редакция, фрагмент
    sources.py               # импорт и сохранение исходных байтов
    extract.py               # PDF, таблицы и адаптер OCR
    parse_cirs.py            # структура конкретного семейства документов
    versions.py              # редакции, доказательства и применимость
    chunk.py                 # чистые функции формирования фрагментов
    embeddings.py            # OpenAI API и кеш
    index.py                 # идемпотентная запись корпуса и embeddings в PostgreSQL
    graph.py                 # последовательный граф и checkpoints
    cli.py                   # команды управления конвейером
  retrieval/
    search.py                # SQL-фильтры, pgvector, FTS и RRF для CLI и инструмента
migrations/                  # миграции Alembic: схема, расширение vector и индексы
tests/
  fixtures/cirs/              # небольшой вручную проверенный образец
  ingestion/
  retrieval/
data/                        # исходные PDF, промежуточные артефакты и отчёты
```

Оставить чистые преобразования отдельно от файловой системы и API; данные проверять на входных границах. Специализацию CIRS держать в его парсере. Поддержку FAQ и документов AT добавлять отдельными адаптерами к той же модели, когда появятся реальные образцы.

Проектный CLI для последовательной реализации:

```text
uv run atrag ingest snapshot
uv run atrag ingest inspect --source docs/CIRS.pdf
uv run atrag ingest prepare --source docs/CIRS.pdf
uv run atrag db migrate
uv run atrag ingest index --prepared data/runs/<run_id>/manifest.json
uv run atrag ingest verify --release <release_id>
uv run atrag ingest publish --release <release_id>
uv run atrag search --query "artigo 16.º CIRS" --tax-year 2024
uv run atrag search --query "How is tax residency determined in Portugal?" --language en --tax-year 2024
```

`snapshot` уже реализован и использует локальный путь из реестра. Остальные команды служат контрактом будущей реализации. `prepare` допускает самостоятельный локальный запуск без подключения к базе и платных вызовов, завершаясь артефактами и отчётом. `db migrate` подготавливает схему PostgreSQL и служебные таблицы checkpointer. `index` использует проверенные фрагменты, создаёт embeddings и записывает подготовленный выпуск в PostgreSQL; выполнение через граф с постоянными checkpoints требует подключения к базе.

## 9. Условия завершения первой части

- Из чистого окружения с `.env` воспроизводится подготовка CIRS; при доступной PostgreSQL с pgvector и ключе OpenAI - загрузка корпуса, индексация и проверка поиска.
- Для каждого фрагмента можно восстановить исходный текст, акт, структуру, редакцию, URL, страницы и доказательства применимости.
- Оригиналы, исключения, ссылки, таблицы и типы источников сохранены; выявленные пробелы отражены в отчёте и выдаче.
- Повторный запуск и восстановление после сбоя не создают дубликаты; неизменяемые фрагменты и embeddings используются повторно между выпусками. Готовый выпуск публикуется транзакционно целиком и допускает откат.
- Поиск на русском, английском и португальском и точные адреса проходят приёмочные проверки. Вопрос за 2024 год на любом из этих языков получает подтверждённую редакцию либо явное сообщение о недостаточном покрытии.
- Сервис поиска готов к подключению как инструмент будущего чата; результат включает всё необходимое для ответа с проверяемыми ссылками.
