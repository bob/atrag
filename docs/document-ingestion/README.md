# План обработки CIRS.pdf и поиска по документу

Статус: реализованы Шаги 1–4 раздела 5 — настройки, регистрация источника, неизменяемый снимок, извлечение с координатами и юридическая структура. Первый источник: [CIRS.pdf](../CIRS.pdf). Доступны `config check`, `ingest snapshot`, `ingest inspect` и `ingest parse`; остальные этапы, `db migrate` и `search` описывают будущую реализацию. Запуск готовых команд описан в [README проекта](../../README.md).

Цель первой версии: разобрать один фиксированный CIRS.pdf, подготовить фрагменты и обеспечить поиск по его содержимому в PostgreSQL с pgvector. Каждый результат должен ссылаться на загруженный PDF, статью/пункт и страницы. Следующий этап после реализованных Шагов 1–4 — Шаг 5, формирование фрагментов.

Упрощение согласовано 30.10.2026: проверка исторических редакций и периодов вынесена за пределы первой версии. Поиск работает по содержимому выбранного снимка PDF; налоговый год и подтверждение юридических дат для этого не требуются.

Стек проекта: Python, LangGraph, Streamlit, OpenAI API, PostgreSQL и pgvector. Здесь проектируем загрузку, извлечение, структурирование, embeddings, индексацию и проверку поиска. Чат в Streamlit и LangGraph-агент, вызывающий поисковый инструмент, относятся ко второй части. Для неё первая часть предоставляет общий поисковый сервис и сведения об ограничениях корпуса.

Решение от 30.10.2026: основным хранилищем проекта выбран PostgreSQL. Источник, структура документа, фрагменты и embeddings хранятся в таблицах; pgvector обеспечивает поиск по embeddings, встроенный полнотекстовый поиск PostgreSQL дополняет его. Это решение заменяет первоначальный выбор Weaviate.

Решение от 30.10.2026: подготовка документов выполняется локально. Получение снимка, извлечение PDF, OCR, ручная сверка, разбор структуры и формирование фрагментов относятся к локальной среде. На прод передаются PDF, подготовленные данные и метаданные; сервер выполняет индексацию в PostgreSQL и проверку поиска. Tesseract и языковые модели нужны только в среде подготовки. Документы и артефакты доставляются отдельно от Git; упаковку и импорт пакета реализовать вместе с индексацией.

## 2. Правила корпуса

1. **Португальский оригинал является основным текстом.** Хранить исходный PDF и извлечённые фрагменты на `pt`. Поддержать вопросы на русском (`ru`), английском (`en`) и португальском (`pt`); использовать единую модель мультиязычных embeddings. Переводы не заменяют оригинал и не требуют отдельных копий корпуса. Качество проверяется на одинаковых по смыслу запросах на всех трёх языках.
2. **Границы определяются структурой документа.** Акт → глава → раздел → статья → номерной пункт (`número`) → подпункт (`alínea`). Короткую статью можно индексировать целиком; длинную делить по пунктам.
3. **Фрагмент сохраняет условия применения.** В него входят заголовок, вводная часть родительского пункта, исключения, оговорки и редакционные примечания, относящиеся к этому положению. Связанные положения доступны через идентификаторы; непроверенная автоматическая сводка не заменяет текст нормы.
4. **Источник сохраняется до ответа пользователю.** Каждый фрагмент связан с `snapshot_id`, названием документа, отметкой редакции сборника и страницами PDF.
5. **Примечания и отметки статуса сохраняются как сведения документа.** Неизвестные юридические даты остаются неизвестными; они не блокируют обработку и поиск по PDF.
6. **Поиск сочетает векторы, полнотекстовый поиск и точные SQL-фильтры.** Обозначение статьи обрабатывается как структурированный адрес. Поиск CIVA не должен возвращать одноимённую статью CIRS.

## 3. Модель данных первой версии

Использовать три связанные сущности. `SourceSnapshot` и `LegalUnit` уже реализованы; `SearchFragment` добавляется на Шаге 5.

| Сущность | Назначение |
| --- | --- |
| `SourceSnapshot` | Неизменяемые байты конкретного документа, происхождение и даты получения |
| `LegalUnit` | Адрес статьи, пункта или подпункта; текст, структура, примечания и локаторы в снимке |
| `SearchFragment` | Единица поиска с необходимым контекстом и ссылками на юридические единицы и снимок |

Основное хранилище — таблицы PostgreSQL: `source_snapshots`, `legal_units`, `search_fragments` и кеш embeddings. Связи закрепить внешними ключами; вхождение юридической единицы определяется парой `(snapshot_id, legal_unit_id)`. PDF остаётся неизменяемым файлом; JSON/JSONL служат промежуточными артефактами, экспортом и материалом для проверки. После индексации поиск читает данные из PostgreSQL.

Для первой версии достаточно одного явно выбранного снимка и его поискового индекса. Первичные ключи, ограничения уникальности и проверки допустимых значений закрепить миграциями. Историю редакций норм и отдельную систему выпусков корпуса отложить.

### Библиотеки и взаимодействие с БД

Набор согласован с пользователем 30.10.2026. На Шаге 1 версии закреплены в `uv.lock`; установка и интеграционные тесты прошли на Python 3.14.6 с локальным PostgreSQL 16.13 и серверным pgvector 0.8.7. Миграции схемы корпуса относятся к последующей реализации.

| Библиотека / пакет | Роль |
| --- | --- |
| [SQLAlchemy 2.x](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#psycopg) | Типизированные ORM-модели таблиц, запросы, транзакции и пул соединений |
| [Psycopg 3](https://www.psycopg.org/psycopg3/docs/basic/install.html), пакет `psycopg[binary,pool]` | Драйвер PostgreSQL |
| [pgvector для Python](https://github.com/pgvector/pgvector-python), пакет `pgvector` | Тип вектора и операции поиска в SQLAlchemy; серверное расширение `vector` устанавливается отдельно |
| [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html) | Миграции схемы, ограничений и индексов; включение расширения `vector` |
| [langgraph-checkpoint-postgres](https://docs.langchain.com/oss/python/langgraph/add-memory#use-in-production) | Установлен для будущего графа; обработка одного PDF пока использует обычные функции и файловые артефакты |
| [python-dotenv](https://bbc2.github.io/python-dotenv/) | Единая загрузка настроек из `.env` |

- Для первой версии выбрать синхронный доступ. `db.py` создаёт SQLAlchemy Engine и фабрику сессий; пул соединений переиспользуется внутри процесса. Каждая операция получает собственную сессию, которая закрывается после завершения. Между потоками и пользователями Streamlit изменяемая сессия не разделяется, согласно [правилам SQLAlchemy](https://docs.sqlalchemy.org/en/21/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks).
- Доступ к корпусу оформить узкими функциями загрузки подготовленного документа и поиска. Обычные операции используют ORM; FTS, векторный поиск и RRF — SQLAlchemy Core либо параметризованный SQL. Парсер и правила формирования фрагментов остаются чистыми преобразованиями данных.
- Для повторной загрузки использовать уникальные ключи и `INSERT ... ON CONFLICT`. Для одного PDF записывать подготовленный набор в одной транзакции; вызовы OpenAI выполнять до неё. Ошибка записи должна оставлять предыдущий индекс доступным.
- Сохранить один канонический `DATABASE_URL` вида `postgresql://...` для приложения и миграций. В `db.py` для SQLAlchemy строить объект URL с явно выбранным драйвером `postgresql+psycopg`.
- Схему корпуса изменять через проверенные миграции Alembic; автогенерацию просматривать вручную. Обязательный граф и настройка checkpointer отложены до появления потребности в длительном конвейере.

### Обязательные метаданные

| Группа | Поля и смысл |
| --- | --- |
| Источник | `source_id`, `snapshot_id`, `source_url`, `source_url_status`, `local_path`, `source_sha256`, `publisher`, `language` - язык документа, для оригинала CIRS `pt`; он не зависит от языка вопроса |
| Тип | Для CIRS `document_type=law`; существующий реестр также допускает другие типы для будущих источников |
| Адрес | `instrument_id`, `code`, `document_scope`, `chapter`, `section`, `article`, `paragraph`, `subparagraph`, `legal_unit_id`, `parent_id` |
| Название | `document_title`, `unit_title`, `citation_label`, нормализованные обозначения для поиска |
| Сведения источника | `consolidation_label`, известные `publication_date`, `revision_publication_date`, `downloaded_at`; фактический `ingested_at` |
| Отметки документа | `legal_status`: `repealed` или `unknown`; роли и редакционные примечания, извлечённые из PDF |
| Текст | `text_original`, `text_normalized`, `embedding_text`, `context_unit_ids`, `references`, `editorial_notes`, `tables` |
| Локатор | `page_start`, `page_end` как физические страницы PDF с нумерацией от 1; `printed_page_labels`, координаты исходных блоков |
| Качество | `extraction_method`, `review_status`, обнаруженные пропуски, неопределённые ссылки и проблемы таблиц |
| Воспроизводимость | `snapshot_id`, `schema_version`, `parser_version`, `chunker_version`, `embedding_model`, `embedding_dimensions`, `embedding_input_hash`, `fragment_id` |

Неизвестные значения явно остаются неизвестными. Например, у локального CIRS `downloaded_at` неизвестен; фактическое время импорта записывается в `ingested_at` в UTC. Отметка обновления сборника хранится в `consolidation_label`. Поле `validity_status=unknown` уже есть в отчёте разбора и может сохраняться как справочное; оно не является условием допуска фрагментов к поиску.

Адреса должны различать, например:

```text
pt:cirs:code:article:16:paragraph:1:subparagraph:a
pt:cirs:code:article:68-A
pt:decreto-lei:442-a/88:approving_decree:article:1
pt:cirs:code:article:1
```

`article` хранить строкой: `68-A`, а не числом. `references` содержат исходное обозначение, найденные адреса и статус разрешения. Ссылки разрешаются внутри того же снимка PDF; внешние и неоднозначные остаются неразрешёнными.

### Шаг 2. Неизменяемый снимок

Выполнен 30.10.2026: модель `SourceSnapshot` в `src/atrag/schemas/ingestion/snapshots.py`, импорт в `src/atrag/ingestion/services/snapshots.py` и команда `uv run atrag ingest snapshot [--registry путь.json]`. Импорт локальный, без БД и OpenAI; исходник не изменяется. SHA-256 служит `snapshot_id`, а UUID попытки записывается отдельно в `data/runs/<run_id>/manifest.json`.

Манифест `data/raw/<sha256>/manifest.json` сохраняет размер, относительный путь к копии, `ingested_at` в UTC и первоначальный реестр в поле `source`. Неизвестные даты остаются `null`, URL сохраняет исходный статус. Повторная попытка проверяет целостность и переиспользует первый снимок; её происхождение записывается в журнале попытки, в том числе при другом реестре с теми же байтами. Каталог с PDF и манифестом публикуется атомарным переименованием; конкурирующие попытки используют один снимок. Повреждение или неполный существующий снимок останавливают импорт без перезаписи. В журнале фиксируются успешные и неудачные попытки; аварийное завершение процесса может оставить статус `running`.

- Импортировать `docs/CIRS.pdf` без изменения исходника. Для будущего скачивания проверять домен, HTTP-статус, MIME и сигнатуру PDF, ограничивать размер и время ожидания.
- Сохранить копию в `data/raw/<sha256>/source.pdf` и манифест с происхождением, контрольной суммой и фактическими датами. При повторном импорте тех же байтов использовать существующий снимок.
- Отдельный `run_id` идентифицирует попытку исполнения. Не включать время запуска в идентификатор снимка или ключ кеша.

### Шаг 6. Embeddings через OpenAI API

Для первого измерения использовать `text-embedding-3-small`, 1536 измерений; `text-embedding-3-large` оставить кандидатом для сравнения на наборе запросов на русском, английском и португальском. Мультиязычная поддержка и размерность описаны в [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/embeddings).

- Вычислять векторы в приложении и сохранять их в PostgreSQL через pgvector. Так модель, повторные попытки и кеш контролируются в одном месте.
- Перед запросом проверять непустой ввод и ограничения выбранной модели по токенам и размеру пакета. Проверять соответствие числа, порядка и размерности ответов входным фрагментам.
- Кешировать в таблице embeddings с уникальным ключом `(model, dimensions, embedding_input_hash)`, независимо от времени запуска. Фрагменты ссылаются на сохранённые векторы. Повторный импорт не должен заново оплачивать уже сохранённые векторы.
- Для временных ошибок использовать ограниченные повторные попытки с задержкой и jitter; ошибки авторизации и данных останавливают этап. Сохранять результаты успешных пакетов и расход токенов.
- Документы и запросы векторизовать одной моделью, размерностью и согласованной схемой подготовки текста. Смена модели требует отдельного пространства embeddings и переиндексации. Проверять совместимость размерности с типом pgvector и выбранным индексом; векторы разных моделей не смешивать даже при одинаковой размерности.

### Шаг 7. PostgreSQL, pgvector и гибридный поиск

Создать миграции реляционной схемы и включить расширение `vector`. Для стартовой модели использовать `vector(1536)`, для полнотекстового индекса - `tsvector` и GIN. Гибридный поиск объединяет два списка кандидатов через Reciprocal Rank Fusion (RRF), а не складывает несопоставимые исходные оценки. Такой подход описан в [документации pgvector](https://github.com/pgvector/pgvector#hybrid-search). Стандартное ранжирование PostgreSQL FTS отличается от BM25.

- Из `text_normalized`, `unit_title` и `document_title` формировать взвешенный `tsvector` с португальской конфигурацией. Проверить нормализацию и стоп-слова на юридических формулировках. Использовать `tsquery` и `ts_rank_cd` согласно [документации PostgreSQL FTS](https://www.postgresql.org/docs/current/textsearch-controls.html).
- Идентификаторы, `snapshot_id`, кодекс, область акта, номер статьи и статусы хранить в типизированных колонках с подходящими SQL-индексами. Точные обозначения искать по этим колонкам, независимо от полнотекстовой нормализации.
- Известные даты источника хранить как `date`, моменты загрузки как `timestamptz`. Для дополнительных данных использовать `jsonb`, но поля фильтрации и связи не прятать в непрозрачную JSON-строку. Таблицы редакций и применимых лет в первой версии не нужны.
- Для точного запроса нормализовать `artigo 53.º CIVA`, `art. 53 CIVA`, `CIVA 53` в `(code=CIVA, article=53)`. Сначала применять фильтр снимка и адреса. Если загружен только CIRS, возвращать `no_match` с указанием отсутствующего документа.
- Для смыслового запроса искать среди фрагментов выбранного снимка PDF. На небольшом корпусе выполнять точный поиск по косинусному расстоянию и полнотекстовый поиск среди того же набора; объединять ранги через RRF и затем выбирать результаты. Фильтры по подтверждённым юридическим периодам не применяются.
- HNSW добавлять после измерений. При приближённом поиске фильтрация может уменьшать число найденных кандидатов; проверить iterative scans, полноту результатов и план SQL-запроса. Особенности описаны в [документации pgvector о фильтрах](https://github.com/pgvector/pgvector#filtering).
- Для русских и английских запросов не рассчитывать на совпадение слов с португальским текстом в FTS. Сначала измерить мультиязычный векторный поиск; при необходимости добавить португальскую поисковую формулировку, сохраняя точные обозначения и исходный вопрос на любом из поддерживаемых языков. Перевод запроса не изменяет корпус.
- Один и тот же фильтр `snapshot_id` и ограничения адреса использовать в обеих ветвях поиска. После объединения добавлять родительские условия/исключения и разрешённые ссылки из того же снимка; контролировать бюджет контекста.

Манифест перечисляет файлы, SHA-256 и версии обработки; пути внутри пакета относительные. Доставка и импорт проверяют контрольные суммы и используют готовые данные без повторного PDF/OCR-разбора.
- До изменения поискового индекса подготовить embeddings и проверить все входы. Для одного PDF сохранить источник, структуру, полный набор фрагментов и связи в одной транзакции; повторная загрузка не создаёт дубликаты. При изменении разбиения заменять набор фрагментов этого снимка целиком. Ошибка откатывает изменение; незавершённый индекс не становится доступным поиску.

## 6. Граница со второй частью: контракт поиска

Реализовать и проверить сервис независимо от Streamlit и затем обернуть его инструментом LangGraph:

```text
search_tax_documents(query, limit=5, query_language=None)
```

Сервис ищет по одному явно выбранному проиндексированному снимку CIRS.pdf. Период вопроса не является обязательным аргументом или фильтром. Результат всегда указывает `snapshot_id` и отметку редакции загруженного сборника; историческую применимость сервис не устанавливает.

`query_language` принимает `ru`, `en` или `pt`; набор поддерживаемых языков определить в одном общем типе. Язык можно указать явно; иначе определять его на входной границе. Для коротких обозначений вроде `CIRS 16`, где определение ненадёжно, приложение передаёт язык интерфейса. Язык вопроса не используется как фильтр языка исходных документов: английский и русский вопросы должны находить португальские нормы.

Во второй части пользователь сможет выбрать язык ответа: русский, английский или португальский. По умолчанию чат отвечает на языке вопроса, а явный выбор языка ответа имеет приоритет. Поисковый сервис возвращает оригинальные португальские фрагменты; чат может объяснять их на выбранном языке, сохраняя оригинальные цитаты, обозначения актов и ссылки.

Результат содержит:

- `status`: `ok` или `no_match`; `snapshot_id`, название документа, `consolidation_label` и установленный `query_language`;
- найденные португальские фрагменты с оценками, актом/статьёй/пунктом, URL и страницами;
- необходимый родительский контекст, исключения, таблицы, редакционные примечания, отметки отмены и ссылки;
- известные пропуски извлечения, неразрешённые ссылки и причину отсутствия результата, например отсутствие запрошенного кодекса.

Будущий чат объясняет содержание найденного документа с цитатами и страницами. Поиск по этому PDF доступен без обязательного уточнения налогового года. Проверка действия нормы в конкретном году остаётся отдельным будущим режимом.

| 1. Настройки и реестр — выполнен | `.env.example`, типы, реестр источника, фабрика Engine | Приоритет окружения, скрытие секретов, проверка реестра и подключения |
| 2. Снимок — выполнен | PDF и манифест | SHA-256, сохранение оригинала, повторный импорт |
| 3. Извлечение — выполнен | `pages.jsonl`, `tables.json`, OCR и отчёт | Физические/печатные страницы, таблицы 68/68-A и известные пропуски |
| 4. Структура — выполнен | `legal_units.jsonl` | Оглавление не создаёт дубликаты; различаются декрет/CIRS, `2`/`2-A`, пункты и отметки отмены |
| 5. Фрагменты | `fragments.jsonl`, отчёт качества | Родительские условия, отрицания, исключения, ссылки и обе части таблицы 68 сохранены |
| 6. Векторизация | Кеш и отчёт использования API | Проверка входа/выхода, повтор пакета после сбоя; повторный импорт использует кеш |
| 7. Индексация | Пакет для переноса, миграции и индекс одного снимка в PostgreSQL с pgvector и FTS | Контрольные суммы, целостная транзакция, отсутствие дубликатов, сохранение предыдущего индекса при ошибке |
| 8. Проверка поиска | Поисковый сервис и отчёт оценки | Точные и смысловые запросы на `ru`, `en`, `pt`, цитаты и страницы, повторный запуск и обработка ошибок |

Подготовить небольшой эталонный набор с ожидаемыми `legal_unit_id`, страницами и обязательным контекстом:

- тройки русских/английских/португальских вопросов о теме статьи 16 без указания номера, например «Как определяется налоговое резидентство в Португалии?», «How is tax residency determined in Portugal?», «Como se determina a residência fiscal em Portugal?»; ожидаемые положения и обязательный контекст совпадают;
- явный выбор языка, определение языка полного вопроса и короткое обозначение с языком интерфейса; английский вопрос находит документ с `language=pt`;
- точные варианты обозначения CIRS 16, CIRS 68-A и CIVA 53; последний даёт `no_match` с указанием отсутствующего документа;
- пункт с исключением и отсылкой: результат содержит необходимые связанные положения, а не только удобную цитату;
- таблица 68 с продолжением и таблица 68-A после OCR: строки и столбцы совпадают с ручным эталоном;
- положение с отметкой отмены и переходное примечание сохраняют текст и роль из PDF;
- запрос без налогового года возвращает релевантные фрагменты; `validity_status=unknown` не исключает весь документ из поиска;
- каждый результат содержит выбранный снимок, отметку редакции сборника и страницы; известные пропуски извлечения остаются видимыми.

Для всех трёх языков повторить случаи с исключениями, таблицами и отсутствующим кодексом: смена языка не меняет выбранный документ. При реализации чата отдельно проверить ответ на английском и приоритет явно выбранного языка ответа.

Предлагаемые критерии MVP: точные адресные запросы проходят весь эталонный набор; для смысловых запросов целевая доля попаданий ожидаемого положения в top-5 не ниже 90% отдельно для русского, английского и португальского. Отдельно измерять полноту обязательного контекста, корректность цитат, задержку и расход токенов. Сравнить vector-only, PostgreSQL FTS и hybrid с RRF; параметры выбирать по результатам. HNSW добавлять только при измеренной необходимости.

Модульные проверки парсера и поиска не требуют сети. Интеграционные проверки PostgreSQL/pgvector выполнять в отдельной тестовой базе с теми же миграциями; проверять ограничения, откат транзакций и повторную загрузку. Настоящий вызов OpenAI — отдельная небольшая проверка с настроенным ключом. При реализации нового поведения применять `crapper`, `dryer` и `mutator` из `tools/ub-mode`: снижать CRAP ниже 10, устранять дублирование с рейтингом от 0.8, проверять выжившие мутации и удалять мёртвый код.

## 8. Предлагаемая структура реализации

```text
src/atrag/
  settings.py                # единственная точка чтения .env и окружения
  cli.py                     # команды подготовки, индексации и поиска
  db.py                      # SQLAlchemy Engine, фабрика сессий и адаптация DATABASE_URL
  db_models.py               # типизированные ORM-модели таблиц корпуса
  schemas/
    settings.py              # схема настроек приложения
    ingestion/               # источники, снимки, извлечение, OCR, структура и будущие фрагменты
  ingestion/
    services/
      sources.py             # загрузка реестра источника
      snapshots.py           # импорт и сохранение исходных байтов
      extract.py             # извлечение PDF и таблиц
      ocr.py                 # адаптер локального Tesseract
      structure.py           # файловый этап структурного разбора
      embeddings.py          # OpenAI API и кеш
      index.py               # загрузка одного подготовленного снимка в PostgreSQL
    extraction.py            # чистые преобразования страниц и таблиц
    parse_cirs.py            # структура конкретного семейства документов
    legal_references.py      # разрешение локальных юридических отсылок
    chunk.py                 # чистые функции формирования фрагментов
  retrieval/
    search.py                # SQL-фильтры, pgvector, FTS и RRF для CLI и инструмента
migrations/                  # миграции Alembic: схема, расширение vector и индексы
tests/
  fixtures/cirs/              # небольшой вручную проверенный образец
  ingestion/
  retrieval/
data/                        # исходные PDF, промежуточные артефакты и отчёты
```

Оставить чистые преобразования отдельно от файловой системы и API; данные проверять на входных границах. Специализацию CIRS держать в его парсере. Схемы фрагментов, `chunk.py`, сервисы embeddings/индексации, ORM-модели, миграции и поиск ещё предстоит реализовать. Новые типы источников и граф обработки относятся к будущим расширениям.

Проектный CLI для последовательной реализации:

```text
uv run atrag ingest snapshot
uv run atrag ingest inspect --source docs/CIRS.pdf
uv run atrag ingest parse --extracted data/runs/<extraction_run_id>/manifest.json
uv run atrag ingest chunk --parsed data/runs/<parse_run_id>/manifest.json
uv run atrag ingest prepare --source docs/CIRS.pdf
uv run atrag db migrate
uv run atrag ingest index --prepared data/runs/<run_id>/manifest.json
uv run atrag ingest verify --snapshot <snapshot_id>
uv run atrag search --query "artigo 16.º CIRS"
uv run atrag search --query "How is tax residency determined in Portugal?" --language en
```

`snapshot` и `inspect` уже реализованы и используют локальный путь из реестра; `inspect --source` позволяет явно переопределить путь. Реализованный `parse --extracted` продолжает успешный запуск `inspect`. Остальные команды служат контрактом будущей реализации. `chunk` формирует фрагменты из готового разбора; `prepare` объединяет локальную подготовку до фрагментов и отчёта без БД и платных вызовов. `db migrate` подготавливает схему PostgreSQL. `index` принимает пакет с манифестом подготовленных данных, создаёт или использует кешированные embeddings и загружает один снимок в PostgreSQL. `verify` проверяет его индекс и поиск; отдельная команда публикации в первой версии не нужна.

## 9. Условия завершения первой части

- Из чистого окружения с `.env` воспроизводится подготовка CIRS; при доступной PostgreSQL с pgvector и ключе OpenAI - загрузка корпуса, индексация и проверка поиска.
- Для каждого фрагмента можно восстановить исходный текст, акт, структуру, снимок PDF, отметку редакции сборника, URL и страницы.
- Оригиналы, исключения, ссылки, таблицы и типы источников сохранены; выявленные пробелы отражены в отчёте и выдаче.
- Повторный запуск после сбоя не создаёт дубликаты; готовые embeddings используются повторно. Загрузка одного снимка в индекс выполняется транзакционно целиком, ошибка сохраняет предыдущий индекс.
- Поиск на русском, английском и португальском и точные адреса проходят приёмочные проверки. Налоговый год не обязателен; результаты относятся к явно указанному снимку документа.
- Сервис поиска готов к подключению как инструмент будущего чата; результат включает всё необходимое для ответа с проверяемыми ссылками.

## 10. Будущие расширения

Эти задачи не входят в приёмку первой версии и не блокируют поиск по CIRS.pdf:

- **Исторические редакции и применимость.** Бывший Шаг 5: поиск изменяющих актов, проверка дат и переходных условий по официальным источникам, модель `NormVersion`, подтверждённые периоды и налоговые годы. При появлении такого требования отдельно спроектировать поиск по периоду и поведение при отсутствии исторических данных.
- **Несколько документов и типов источников.** Другие кодексы, инструкции AT, индивидуальные разъяснения и FAQ, отдельные адаптеры и явный выбор источника.
- **Выпуски корпуса и длительные процессы.** Управление несколькими выпусками, переключение активного выпуска и откат; LangGraph с checkpoints при необходимости возобновлять длительные конвейеры.

История подготовки этого плана: [журнал действий](ACTION_LOG.md). Ранние записи описывают требования, действовавшие до упрощения от 30.10.2026.
